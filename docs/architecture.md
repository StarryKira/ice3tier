# ice3tier 架构与内部约定

这份文档写给读代码和写代码的人：各个 crate 管什么、它们之间怎么对接、线上跑的是什么。逐字节的格式以 `crates/i3t-proto` 里的文档注释为准；controller 的管理接口见 [admin-api.md](admin-api.md)，发布与更新见 [releasing.md](releasing.md)。

## 1. 一句话

ice3tier 是一个不用虚拟网卡的组网工具。一对节点之间只有一条端到端的 QUIC 连接，每条用户连接是其中的一个流。这条连接的包能直连就直连，不能就经 relay 转发；relay 只转发包，解不开内容。走哪条路可以随时换，连接和上面的流不受影响。

## 2. 分层与 crate

每层只依赖下面一层。

| crate | 管什么 |
|---|---|
| `i3t-proto` | 线上格式：数据报分类、中转头、中转会话帧、探测帧、建流请求。不做 I/O |
| `i3t-model` | 控制面的数据：节点收到的 netmap、节点与 controller 之间的消息、管理 API 的数据结构。只有类型和 serde |
| `i3t-crypto` | 节点密钥（Ed25519）、签名、用节点密钥签出来的 TLS 证书、按公钥校验对端的 TLS 校验器 |
| `i3t-underlay` | 一个 UDP 端口：绑定、批量收发；本机网卡地址；地址查询；端口映射；局域网发现 |
| `i3t-path` | 包怎么送到对端：到每个对端当前走哪条路（直连、经哪个 relay、UDP 还是 TCP）；中转会话；探测；打洞；选路与换路 |
| `i3t-relay` | relay 一侧：会话表、转发、限速 |
| `i3t-conn` | 端到端连接：QUIC 跑在 `i3t-path` 上；按对端管理连接；自己的拥塞控制 |
| `i3t-flow` | 建流请求与应答、两个方向的搬运、数据报上下文 |
| `i3t-lane` | 可选的另一种传输：一对节点之间每条流独占一条 TCP 连接（见 5.8）。它实现的是 `i3t-conn` 里同一份"开流、接流"的约定，所以上面几层不用区分 |
| `i3t-access` | 入口：SOCKS5、HTTP CONNECT、端口转发的监听；用户名解析；凭据 |
| `i3t-exit` | 出口：访问控制、出站策略、解析域名、连接目标。它依赖 `i3t-access` 里"就地出站"的接口，这样入口的就地出站和出口用的是同一套出站策略和同一份 DNS 缓存 |
| `i3t-agent` | 把上面这些装成一个节点：连 controller、应用 netmap、上报、本机管理接口 |
| `i3t-controller` | controller：存储、注册、访问规则编译、给每个节点算 netmap、节点协议、管理 API |
| `i3t-update` | 节点更新：验签、取包、自检、替换、回退 |
| `i3t-metrics` | 指标 |
| `bins/i3t`、`bins/i3tctl`、`bins/i3t-controller` | 三个可执行文件 |
| `web/` | WebUI（React） |

两条结构上的约束：

- `i3t-conn` 不碰 socket，收发包都经过 `i3t-path`。所以"换路不断流"是 `i3t-path` 这一层的性质。
- QUIC 库的类型不出 `i3t-conn`。上层只看到"到某个节点开一条流"和"某个节点开过来一条流"。

## 3. 身份与认证

只有一种密钥：每个节点一对 Ed25519 密钥，本地生成，私钥不离开节点。公钥 32 字节，文本形式是不带填充的 base64url。

| 场合 | 怎么认证 |
|---|---|
| 节点 ↔ 节点（QUIC） | TLS 1.3 双向认证。双方的证书都是用自己的节点密钥自签的；校验器不看证书链，只取证书里的公钥，和 netmap 里这个对端的公钥比对。ALPN 是 `i3t/1` |
| 节点 ↔ controller | TCP 上的 TLS 1.3，双向认证，做法同上：节点事先知道 controller 的公钥（写在注册令牌里），controller 按公钥认节点 |
| 节点 ↔ relay（中转会话） | 一次带签名的握手，见 §5.2 |
| 节点 ↔ 节点（探测、打洞） | 每个探测包带发送方的签名，见 §5.3 |
| 发布包 | 发布清单带签名，节点用编译在程序里的公钥验 |

不用 Noise。所有需要加密的通道都是 rustls 的 TLS 1.3，其余只需要认证的地方用 Ed25519 签名。

## 4. 控制面：netmap

节点运行所需要的一切配置都在一个 `Netmap` 里（`i3t-model`），由 controller 按最小权限为每个节点单独算出来，带版本号下发。节点把最后一份成功应用的 netmap 存在本地，controller 不在线时照常工作。

netmap 也可以从一个 JSON 文件读（静态模式，`i3t run --static <文件>`）。这是测试用的：数据面的测试不需要 controller。

节点和 controller 之间的消息是 TLS 连接上的帧：4 字节大端长度，后面是一个 JSON 对象（`i3t-model::control`）。收的一方忽略不认识的字段，新旧版本可以共存。

## 5. 数据面

### 5.1 一个端口，按首字节分类

节点只绑定一个 UDP 端口（默认 20330）。收到的数据报按首字节分：

| 首字节 | 是什么 | 交给谁 |
|---|---|---|
| 带 `0x40` 位 | 对端直连发来的 QUIC 包 | 按来源地址查出是哪个对端，交给 `i3t-conn`；来源地址不是任何对端已验证的直连地址时丢掉 |
| `0x01` | 经一个 relay 转发的包（中转头里有目的和来源节点） | 目的是自己：去掉头交给 `i3t-conn`。目的不是自己：本节点启用了 relay 就转发，否则丢掉 |
| `0x0d` | 经多个 relay 转发的包（头里另外列出要依次经过的 relay，1 到 4 个，不能重复） | 同上。relay 只转发自己在路径上、并且来自上一跳的包；里面的包原样不动 |
| `0x02`～`0x07`、`0x0c` | 中转会话帧（握手、保活，`0x0c` 是 relay 的拒绝说明） | 本节点是 relay 时由 `i3t-relay` 处理；relay 的应答由 `i3t-path` 处理，只收从 relay 的地址来的 |
| `0x08`、`0x09` | 探测帧 | `i3t-path` |
| `0x0e` | relay 签名的状态行：它在不在服务（正常、过载、即将下线）、负载、到别的 relay 的延迟和丢包 | `i3t-path`。relay 把自己的行发给所有会话，也把别的 relay 的行传下去 |
| `0x0a`、`0x0b` | 地址查询与应答 | `i3t-underlay` |
| 其余 | 不认识 | 丢掉，不回应 |

relay 另外在同一个端口号上监听 TCP。UDP 用不了的节点连上来，把同样的数据报加上 2 字节长度装进去（`i3t-proto::tcp_frame`），之后的处理和 UDP 完全一样。

### 5.2 中转会话

节点要经某个 relay 收发包，先和它建一个中转会话。relay 凭会话知道这个节点现在在哪个地址上，并且只转发来自已建立会话的节点的包。

```
节点 → relay   INIT       { 节点编号, 随机数 a }
relay → 节点   CHALLENGE  { cookie }                 cookie 由 relay 用自己的密钥对"来源地址 + 节点编号 + 时间片"算出，relay 这时不记任何状态
节点 → relay   AUTH       { 节点编号, 随机数 a, cookie, 签名 }      签名覆盖 relay 的编号、cookie、随机数 a
relay → 节点   OK         { 有效期, relay 看到的节点地址, 签名 }    签名覆盖节点编号、随机数 a
```

- relay 验过 cookie（证明来源地址不是伪造的）才去验签名，所以伪造来源地址的包不会让它做昂贵的运算，应答也不比请求大。验签名本身也限速：每个来源（一个 IPv4 地址，或者一个 IPv6 的 /64）每秒 5 次，全部加起来每秒 200 次，拿着一个 cookie 也不能让 relay 无休止地验下去。
- 会话绑定在来源地址上。之后节点每隔一段时间发 PING，relay 回 PONG（带它看到的地址），用来保活、测延迟、发现自己的公网地址。节点的地址变了（PONG 不来，或者 relay 回 `UNKNOWN`）就重新握手。
- relay 转发 `0x01` 帧时核对：来源节点有会话，并且数据报就是从会话绑定的地址来的；目的节点也有会话。不满足就丢掉，并按来源地址限速地回一个错误帧。
- 错误帧（`0x0c`，14 字节）没有签名，所以带一段回显，节点只认回显对得上的：保活 PING 引出来的回显 PING 的随机数；中转帧引出来的回显那个帧里的前 8 个字节；"对端没挂在我这里""这条路走不通"回显会话握手时的随机数。路径之外的人猜不到这些，伪造来源地址发一个错误帧拆不掉别人的会话。回显对不上的"没有会话"只让节点马上发一个 PING 去问一下。
- 走 TCP 的节点在 TCP 连接上做同样的握手，会话绑定在这条 TCP 连接上。握手要在连上之后 10 秒内完成，握手之前只收握手的帧；每个来源最多占 8 条还没有握手的连接。
- TCP 里的帧不会丢，只会迟到，所以节点在 TCP 上握手不重发，每一步等 4 秒：丢包的链路上 TCP 一次重传就是一两秒，照 UDP 的节奏（半秒重发、两秒放弃）握手会接连失败。保活连续没有回答时不等，照样拆掉重连：真实链路上量过，卡住的 TCP 多数等很久也不恢复，新拨一条通常不到 1 秒就握上手。
- relay 设了带宽上限时，各个来源节点公平地分：桶快空的时候，上一秒已经用掉自己那一份的来源先等着。
- 往 TCP 里写的两头都要限制积压：发送队列有上限（满了丢新来的包），内核里未发出的数据也有上限（`TCP_NOTSENT_LOWAT`）。

### 5.3 直连与探测

一个对端的直连地址要先验证过才能用：

```
A → B   PING  { A, B, 随机数, 签名 }
B → A   PONG  { B, A, 同一个随机数, B 看到的 A 的地址, 签名 }
```

- A 向 B 的某个候选地址发 PING，收到带着同一个随机数、签名正确的 PONG，这个地址才算 B 的已验证直连地址，A 才会往它发连接包。
- B 收到签名正确的 PING 时，把来源地址记为"可以收 A 的包的地址"，并且自己也向它发 PING 做反方向的验证。
- 只凭一个签名正确的 PING，来源地址只被信任 15 秒；本节点自己反方向探测得到回答之后才延长。签名的 PING 可以被人录下来换个来源地址重放，所以它单独不能长期占住一个地址。同一个地址被两个对端声称时，归正在用它的那个。
- PONG 里对端看到的本节点地址要对得上本节点已知的自己的地址，否则不算数：中间夹着一台替两边转发的机器时，这个地址是它的。
- 打洞就是双方在约定的时刻互相向对方的候选地址发 PING。
- 已经在用的直连地址每 5 秒探测一次；连续超时就判为不可用，改走 relay。

候选地址从这几处来，都要经过上面的验证才会用：

- 本机网卡上的地址，以及 relay 和 controller 看到的本节点的外部地址。
- 局域网发现：节点在本地网段上发组播信标，只有已经知道发送方公钥的节点认得出它。同一个局域网里的两个节点由此直接互连，这样的直连无条件优先。
- 端口映射：向路由器申请把节点的端口映射出去（UPnP-IGD、NAT-PMP、PCP），拿到的外部地址作为候选；节点退出时撤销。
- IPv6 地址。节点的端口在系统允许时同时收 IPv4 和 IPv6。

### 5.4 选路

`i3t-path` 为每个对端维护"现在走哪条路"。发包时只查这一个结果，不做别的判断。

- 默认模式：直连可用就走直连；否则经一个 relay。经 relay 时按这个顺序取第一个可用的：
  1. 对端自己就是 relay，并且本节点和它之间有中转会话：直接把包发给它（它收到目的是自己的包就交给连接层）。
  2. 本节点自己是 relay，并且对端在本节点上有会话：用这个会话。
  3. 对端挂靠的 relay，按对端到它们的延迟从低到高。

  前两条不经过第三台机器，所以排在前面。对端挂靠的 relay 之间，现在走着的那个只要没有明显变慢就不换：对端上报的顺序会随测量的起伏来回变。
- 延迟优先模式：列出直连和经 1 到 4 个 relay 的全部路径，按代价比较，取最低的。
  - 代价以毫秒计：各段延迟之和，加上抖动、丢包折算成的延迟，再加上 relay 的负载惩罚。本节点到 relay 的那一段是自己测的；relay 之间的各段来自 relay 发布的状态行；最后一段是对端上报的它到 relay 的延迟。
  - 换路有迟滞：新的路要连续 3 个评估窗口（每个 5 秒）都便宜至少 max(5 ms, 10%)，换过之后至少停留 30 秒。两条路来回换的时候停留期逐次加倍，最长 8 分钟。
  - 现在的路断了就立刻换到剩下的里面代价最低的，不等迟滞。
- 两种模式共同的规则：
  - 到一个 relay 的会话断了又连上之后，要保持满 30 秒，流量才会换回经它的路上。一条时好时坏的链路每次重连之后头几秒看起来总是好的，不这样流量会跟着它一断一连地来回换。从没断过的会话不用等；原来的路断了、只剩它能走的时候也不管这一条。
  - relay 通知自己即将下线或者过载时，节点立刻把路和挂靠挪到别的 relay 上；过载的 relay 恢复之后各节点各等一段随机的时间再回去。
  - relay 之间的一条连接要两头都报了才算数，延迟和丢包取两头里差的那个：一个 relay 不能把自己的连接报得比邻居量到的更好，把流量引到自己身上。
- 两条路对 `i3t-conn` 报同一个最大包长（`i3t-proto::MAX_CONN_PACKET_LEN`）。
- 没有任何路可走时，包被丢掉，连接自己在空闲超时之内等路恢复。

### 5.5 连接

- `i3t-conn` 给每个对端一个固定的虚拟地址（由节点编号算出），QUIC 始终把对端看成这个地址。所以换路时 QUIC 不知道。
- 一对节点一条连接，按需建立，没有流之后 5 分钟关闭（设为常驻的除外）。
- 连接编号的校验密钥和"无状态重置"的密钥都从节点的私钥派生，重启之后不变。节点崩溃重启之后，对端在旧连接上发来的包会得到一个重置，对端立刻知道连接没了、重新拨号；否则要等 30 秒的空闲超时，这期间它开的新流都没有回音。
- 保活 15 秒，空闲超时 30 秒，并发流上限 16384，每条流的接收窗口 2 MB。
- 连接的发送窗口 64 MB：流的优先级只能排已经交给连接的数据，窗口太小时几条大流量的流就能把它占满。
- 连接的接收窗口 64 MB：对端发过来、本端还没有读走的数据，一条连接上所有的流加起来不超过这么多。没有这个上限的话，任何一个对端都能开满流、压满每条流的窗口，把本端的内存吃光。
- 同一个对端最多同时有 2 条连接（两边同时拨号时会有两条）。再来第三条就关掉最老的：守规矩的对端只在手上的连接都不能用了才会重拨，所以最老的那条在它那边已经是死的。
- 进来的握手同时最多处理 64 个，每个对端 4 个。挤的时候，没有验证过来源地址的握手先被要求重试一次（QUIC Retry），伪造来源地址的握手到不了这一步。
- 拥塞控制在 `i3t-conn/src/congestion`，默认是一份按公开草案自己写的 BBR（环境变量 `I3T_CONGESTION=cubic` 可以换回 Cubic 做对比）。QUIC 库自带的 Cubic 把每次丢包都当作拥塞，在有随机丢包的长距离链路上很慢：50 ms、丢包 1% 的 100 Mbit/s 链路上只有 2.6 Mbit/s，BBR 是 87 Mbit/s。库自带的 BBR 带宽估计只升不降，不能用。测量的办法在 `bench/congestion`。

### 5.6 流

每条用户连接是 QUIC 连接上的一条双向流。流上的第一样东西是建流请求（`i3t-proto::flow`），后面直接跟数据：

```
发起方 → 对端   OPEN  { 目标, 服务等级, 来源说明 } 首批数据…
对端 → 发起方   REPLY { 状态, 说明 } 数据…
```

目标有四种：经对端访问互联网（域名或地址加端口）、对端自己的服务（端口）、对端所在局域网里的地址、下发给对端的某一条端口转发（编号）。

发起方是谁由连接的握手确定，流上不再认证。对端收到 OPEN 后按发起节点查访问规则，再按目标类型查自己的能力和出站策略。

接受流的一方在读 OPEN 之前先看发起节点：

- 没有任何一条访问规则允许它访问本节点的，流直接重置，一个字节也不读、不缓存。
- 同一个对端同时在处理的流超过 16384 条的，回"流太多"（状态 `0x27`），同样不读 OPEN。这个数和一条连接上并发流的上限一样，装得下一个网关经同一个出口挂着的几千个请求；它限制的是一个对端最多能占用多少文件描述符。

流没有空闲超时：一条不说话的 SSH 或数据库连接、一个正在等模型思考的请求都是正常的。流两头的每条 TCP（入口上客户端连进来的那条，出口上连目标的那条）都开内核保活，静默 25 秒开始探测。只有一头真的没了，流才会被拆掉。

节点失去一项能力（不再是出口、关了局域网访问、删了端口转发），或者访问规则不再允许某个对端时，靠这一项放行的、正在进行的流立刻被重置，不等它们自己结束。

出口替别人访问互联网时，除了私有、回环这些只在本地有意义的地址，也不去连本节点自己的地址（包括 relay 和 controller 看到的外部地址、路由器上映射出来的地址）和 netmap 里其他节点与 relay 的地址：不然关着"局域网访问"也能经路由器的公网地址摸到它的管理界面。域名解析同时最多 64 个，每个发起方 16 个。

绑定在非回环地址上的代理入口一律要求凭据，不管配置里有没有写。

异常结束用流的重置来传递，不能表现成正常结束：目标一侧异常断开时，对端重置这条流，入口再用 RST 关掉客户端的连接。

### 5.7 UDP 应用的数据与服务等级

UDP 应用的数据（SOCKS5 的 UDP ASSOCIATE、UDP 端口转发）走"数据报上下文"：

- 发起方在一条流上发一个"开数据报上下文"的请求，对端应答之后，这条流就只代表这个上下文的存续：关掉或重置它，上下文就结束。
- 之后的数据报带着上下文的编号，走连接上不可靠的数据报通道。每个数据报自带目标地址，所以一个上下文在出口上对应一个 UDP 套接字，映射与目的地址无关。
- 数据报超过连接允许的大小时，在发送方分片、在接收方重组，重组的内存和时间都有上限。relay 看不到这些。
- 出口对每个目的地址做和流一样的访问规则与出站策略检查。
- 数量有上限：出口上每个对端最多 128 个上下文；一条 UDP 端口转发最多 64 个会话，每个来源地址（一个 IPv4 地址，或者一个 IPv6 的 /64）最多 16 个，本机回环来的不限。

服务等级决定同一条连接上谁先发：交互类的流优先级高，大流量的流让位；`auto`（默认）开始按交互类调度，累计超过 1 MB 之后降为大流量的优先级。等级写在代理用户名的后缀里（`+c-i`、`+c-r`、`+c-b`）。UDP 应用的数据在"不丢包优先"等级下每个数据报单独走一条流，路上不丢；其他等级走不可靠的数据报通道。

### 5.8 独占 TCP（lane）

默认情况下一对节点之间所有的流都在那一条 QUIC 连接里。这有两个代价：丢一个包，连接上不相干的流一起等；内容本身已经是 TLS 的流量还要在 QUIC 里再加密一次。对多数用法无所谓，对"入口和出口之间挂着几千条长时间的 HTTPS 流"（比如网关）就明显了。所以可以按节点对打开另一种传输：每条流独占一条 TCP 连接，叫 lane（`i3t-lane`）。它不是默认的，也不会被自动选中。

**设置。** 每对节点一项，三个取值：不用（默认）、UDP 不通时用、总是用。两个节点里至少有一个要启用为 relay（只有 relay 监听 TCP），否则设置不起作用，管理接口会说明原因。

**连接。**

- lane 由"连得上对方 TCP 端口"的那一方拨向对方的节点端口，也就是 relay 的 TCP 监听用的那个端口。进来的 TCP 按第一个字节分：`0x16`（TLS 握手记录）是 lane，其余的是 relay 的 TCP 接入（开头是 2 字节的长度，高位字节是 0）。
- 每条 lane 是一条 TLS 1.3 连接，两边按 netmap 里的节点公钥互相认证，和节点连 controller 的做法一样。认不出公钥的在握手里就被拒绝。
- 一条 lane 只给一条流用，用完就关，不复用。
- 拨号的一方提前把 lane 拨好、握完手放着：一部分留给自己发起的流，一部分停在对方那里，对方要向这边开流时取一条用。停着的数量跟着新建流的速率变（最多 64 条空闲，突发时一次补拨最多 512 条）。池空了的流最多等 2 秒，等不到就改走 QUIC 连接。
- 两边之间另有一条控制用的 lane：要求"再拨几条"、互相 ping、通知"我要下线了"。拨号方重启或者公网地址变了会换一个代数，对方立刻丢掉旧代数的空闲 lane：家宽重拨之后旧连接不会收到 RST，不这样就会取到死连接。

**一条流。** 发起方在 lane 的 TLS 里发建流请求（和 QUIC 上的相同）和首批数据，对方回复之后：

- **加密模式**：流的字节一直走这条 lane 的 TLS。一个方向结束时先发 TLS 的关闭通知再关 TCP；没有通知就断了算异常结束。
- **透传模式**：首批数据本身是一个完整的 TLS ClientHello 时用。建流的请求和回复交换完之后，这条 TCP 退出 TLS，原样搬运用户的字节，Linux 上用 `splice` 在内核里搬。这些字节本来就是用户和目标之间的 TLS，所以不需要节点再加密；建流请求（里面有目标地址）仍然是加密的。
- 两种模式下，异常结束都以 TCP 的重置传到对面，不会变成正常结束。

**选哪种传输**由发起流的节点对每条流单独决定：只有承载 TCP 连接的流会走 lane，UDP 应用的数据、数据报上下文始终走 QUIC 连接。"UDP 不通时用"看的是这对节点的 QUIC 连接现在有没有 UDP 的路。开不出 lane（池空、对方拒绝、端口连不上）时，在发出任何数据之前悄悄改走 QUIC 连接，并计一次数。已经在跑的流不换传输。

访问规则、出口的带宽和配额、凭据的用量、每个对端的流数上限、排空，在 lane 上和在 QUIC 连接上是同一套代码、同样的行为。lane 上的流不随选路变化（它就是那一条 TCP），节点对之间的 QUIC 连接和它的路由照常保留。

本机实验环境里量到的（同一组网关负载，开和关）：入口和出口合计的 CPU 少三到五成；400 个请求同时到达、各带最多 1 MB 的请求体时，上传的中位数从 342 ms 降到 22 ms；往返 150 ms、丢包 1% 时，一次停顿牵连的流从最多 58 条降到最多 4 条，但每条流要自己握手和慢启动，首字节的中位数从 355 ms 涨到 934 ms。

## 6. 节点更新

节点程序可以自己更新（`i3t-update`，发布流程见 [releasing.md](releasing.md)）：

- 一个发布是一组文件加一份清单，清单用发布私钥签名。节点只信任编译在程序里的公钥，运行时不能增加或替换。
- controller 定期查看发布源（默认是项目的 GitHub Release，可以换成镜像或本地目录），验过签名之后把用得到的包下载一次并缓存。节点不直接连发布源，经到 controller 的那条长连接分块取包，断了可以续传。
- 节点上的步骤：验签、只接受比自己新的版本、核对大小和哈希、运行新程序的自检、原子替换并保留旧程序、重启。新程序连上 controller 才算成功；启动了 3 次或者过了 5 分钟还没连上，节点自己换回旧程序，这个版本不再自动重试。
- 自动更新只在节点没有活跃的流时进行；管理员可以强制立刻更新，或者让节点排空之后更新。relay 一个一个更新。有节点因为版本本身的问题失败时，这个版本在它所在的那个网络里暂停自动更新，等管理员处理；只有 controller 确实让这个节点装过这个版本，它报的失败才算数，免得随便一个节点谎报就能让大家都不更新。
- 排空期间节点不接新的流，入口和出口都会给出明确的拒绝，手上的流照常结束。

## 7. 约定

- Rust 2024，`cargo clippy --workspace --all-targets -- -D warnings` 必须通过。
- 库 crate 的错误类型用 `thiserror`；可执行文件和装配层用 `anyhow`。
