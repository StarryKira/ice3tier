# ice3tier 架构与内部约定

这份文档写给读代码和写代码的人：各个 crate 管什么、它们之间怎么对接、线上跑的是什么。逐字节的格式以 `crates/i3t-proto` 里的文档注释为准；controller 的管理接口见 [admin-api.md](admin-api.md)，发布与更新见 [releasing.md](releasing.md)。

## 1. 一句话

ice3tier 是一个不用虚拟网卡的组网工具。一对节点之间只有一条端到端的 QUIC 连接，每条用户连接是其中的一个流。这条连接的包能直连就直连，不能就经 relay 转发；relay 只转发包，解不开内容。走哪条路可以随时换，连接和上面的流不受影响。

## 2. 分层与 crate

每层只依赖下面一层。

| crate | 管什么 |
|---|---|
| `i3t-proto` | 线上格式：数据报分类、中转头、中转会话帧、探测帧、建流请求。不做 I/O |
| `i3t-model` | 控制面的数据：节点收到的 netmap、节点与 controller 之间的消息、管理 API 的数据结构。只有类型和 serde |
| `i3t-crypto` | 节点密钥（Ed25519）、签名、用节点密钥签出来的 TLS 证书、按公钥校验对端的 TLS 校验器 |
| `i3t-underlay` | 一个 UDP 端口：绑定、批量收发；本机网卡地址；地址查询；端口映射；局域网发现 |
| `i3t-path` | 包怎么送到对端：到每个对端当前走哪条路（直连、经哪个 relay、UDP 还是 TCP）；中转会话；探测；打洞；选路与换路 |
| `i3t-relay` | relay 一侧：会话表、转发、限速 |
| `i3t-conn` | 端到端连接：QUIC 跑在 `i3t-path` 上；按对端管理连接；自己的拥塞控制 |
| `i3t-flow` | 建流请求与应答、两个方向的搬运、数据报上下文 |
| `i3t-lane` | 可选的另一种传输：一对节点之间每条流独占一条 TCP 连接（见 5.8）。它实现的是 `i3t-conn` 里同一份"开流、接流"的约定，所以上面几层不用区分 |
| `i3t-access` | 入口：SOCKS5、HTTP 代理（CONNECT 和明文 HTTP 的转发）、端口转发的监听；用户名解析；凭据 |
| `i3t-exit` | 出口：访问控制、出站策略、解析域名、连接目标。它依赖 `i3t-access` 里"就地出站"的接口，这样入口的就地出站和出口用的是同一套出站策略和同一份 DNS 缓存 |
| `i3t-intercept` | Linux 上的透明访问（5.10）：装进系统里的包过滤规则、策略路由、dummy 网卡和名字服务的应答，拦截要用的几种套接字。不依赖别的 crate，入口、出口和装配层用它 |
| `i3t-agent` | 把上面这些装成一个节点：连 controller、应用 netmap、上报、本机管理接口 |
| `i3t-controller` | controller：存储、注册、访问规则编译、给每个节点算 netmap、节点协议、管理 API |
| `i3t-update` | 节点更新：验签、取包、自检、替换、回退 |
| `i3t-metrics` | 指标 |
| `bins/i3t`、`bins/i3tctl`、`bins/i3t-controller` | 三个可执行文件 |
| `web/` | WebUI（React） |

两条结构上的约束：

- `i3t-conn` 不碰 socket，收发包都经过 `i3t-path`。所以"换路不断流"是 `i3t-path` 这一层的性质。
- QUIC 库的类型不出 `i3t-conn`。上层只看到"到某个节点开一条流"和"某个节点开过来一条流"。

## 3. 身份与认证

只有一种密钥：每个节点一对 Ed25519 密钥，本地生成，私钥不离开节点。公钥 32 字节，文本形式是不带填充的 base64url。

| 场合 | 怎么认证 |
|---|---|
| 节点 ↔ 节点（QUIC） | TLS 1.3 双向认证。双方的证书都是用自己的节点密钥自签的；校验器不看证书链，只取证书里的公钥，和 netmap 里这个对端的公钥比对。ALPN 是 `i3t/1` |
| 节点 ↔ controller | TCP 上的 TLS 1.3，双向认证，做法同上：节点事先知道 controller 的公钥（写在注册令牌里），controller 按公钥认节点 |
| 节点 ↔ relay（中转会话） | 一次带签名的握手，见 §5.2 |
| 节点 ↔ 节点（探测、打洞） | 每个探测包带发送方的签名，见 §5.3 |
| 发布包 | 发布清单带签名，节点用编译在程序里的公钥验 |

不用 Noise。所有需要加密的通道都是 rustls 的 TLS 1.3，其余只需要认证的地方用 Ed25519 签名。

## 4. 控制面：netmap

节点运行所需要的一切配置都在一个 `Netmap` 里（`i3t-model`），由 controller 按最小权限为每个节点单独算出来，带版本号下发。节点把最后一份成功应用的 netmap 存在本地，controller 不在线时照常工作。

netmap 也可以从一个 JSON 文件读（静态模式，`i3t run --static <文件>`）。这是测试用的：数据面的测试不需要 controller。

节点和 controller 之间的消息是 TLS 连接上的帧：4 字节大端长度，后面是一个 JSON 对象（`i3t-model::control`）。收的一方忽略不认识的字段，新旧版本可以共存。

**relay 的地址是 controller 找出来的**（白皮书 §7.2，`i3t-controller` 的 `node_addresses`），没有人填。三处来源按这个顺序合在一起，去掉重复，最多 8 个：
节点上声明的（`i3t set relay-address`，写在节点的配置里，和 `can-*` 一起在 Hello 里报上来）；controller 看到的（这条控制连接的来源 IP
加上节点自报的端口；走回环连过来的换成 `--public-addr` 里的主机）；节点网卡上的（上报里的 `local_addresses`，加上同一个端口）。
netmap 里一个 relay 的 `udp` 和 `tcp` 是同一组。这些来源都存在数据库里，节点离线、controller 重启之后照样算得出来；哪一处变了，全网的
netmap 跟着变。谁连得上 relay，它就是谁的 relay：controller 不按"有没有公网地址""controller 连不连得上"筛地址，也不因此拒绝启用。

**控制面还留着两样给界面的东西。** 节点的网卡地址落在网络的虚拟地址段里时，节点和总览上有一条提醒（`range_overlap`），不拦任何事。
给图表用的低分辨率时间序列（`controller/stats.rs`）：从节点的上报里攒，每 5 分钟一个点留 24 小时，整点汇总成 1 小时一个点留 7 天，
存在同一个数据库里；接口见 [admin-api.md](admin-api.md) 第 20 节。

## 5. 数据面

### 5.1 一个端口，按首字节分类

节点只绑定一个 UDP 端口（默认 20330）。收到的数据报按首字节分：

| 首字节 | 是什么 | 交给谁 |
|---|---|---|
| 带 `0x40` 位 | 对端直连发来的 QUIC 包 | 按来源地址查出是哪个对端，交给 `i3t-conn`；来源地址不是任何对端已验证的直连地址时丢掉 |
| `0x01` | 经一个 relay 转发的包（中转头里有目的和来源节点） | 目的是自己：去掉头交给 `i3t-conn`。目的不是自己：本节点启用了 relay 就转发，否则丢掉 |
| `0x0d` | 经多个 relay 转发的包（头里另外列出要依次经过的 relay，1 到 4 个，不能重复） | 同上。relay 只转发自己在路径上、并且来自上一跳的包；里面的包原样不动 |
| `0x02`～`0x07`、`0x0c` | 中转会话帧（握手、保活，`0x0c` 是 relay 的拒绝说明） | 本节点是 relay 时由 `i3t-relay` 处理；relay 的应答由 `i3t-path` 处理，只收从 relay 的地址来的 |
| `0x08`、`0x09` | 探测帧 | `i3t-path` |
| `0x0e` | relay 签名的状态行：它在不在服务（正常、过载、即将下线）、负载、到别的 relay 的延迟和丢包 | `i3t-path`。relay 把自己的行发给所有会话，也把别的 relay 的行传下去 |
| `0x0a`、`0x0b` | 地址查询与应答 | `i3t-underlay` |
| 其余 | 不认识 | 丢掉，不回应 |

relay 另外在同一个端口号上监听 TCP。UDP 用不了的节点连上来，把同样的数据报加上 2 字节长度装进去（`i3t-proto::tcp_frame`），之后的处理和 UDP 完全一样。

### 5.2 中转会话

节点要经某个 relay 收发包，先和它建一个中转会话。relay 凭会话知道这个节点现在在哪个地址上，并且只转发来自已建立会话的节点的包。

```
节点 → relay   INIT       { 节点编号, 随机数 a }
relay → 节点   CHALLENGE  { cookie }                 cookie 由 relay 用自己的密钥对"来源地址 + 节点编号 + 时间片"算出，relay 这时不记任何状态
节点 → relay   AUTH       { 节点编号, 随机数 a, cookie, 签名 }      签名覆盖 relay 的编号、cookie、随机数 a
relay → 节点   OK         { 有效期, relay 看到的节点地址, 签名 }    签名覆盖节点编号、随机数 a
```

- relay 验过 cookie（证明来源地址不是伪造的）才去验签名，所以伪造来源地址的包不会让它做昂贵的运算，应答也不比请求大。验签名本身也限速：每个来源（一个 IPv4 地址，或者一个 IPv6 的 /64）每秒 5 次，全部加起来每秒 200 次，拿着一个 cookie 也不能让 relay 无休止地验下去。
- 会话绑定在来源地址上。之后节点每隔一段时间发 PING，relay 回 PONG（带它看到的地址），用来保活、测延迟、发现自己的公网地址。节点的地址变了（PONG 不来，或者 relay 回 `UNKNOWN`）就重新握手。
- relay 转发 `0x01` 帧时核对：来源节点有会话，并且数据报就是从会话绑定的地址来的；目的节点也有会话。不满足就丢掉，并按来源地址限速地回一个错误帧。
- 错误帧（`0x0c`，14 字节）没有签名，所以带一段回显，节点只认回显对得上的：保活 PING 引出来的回显 PING 的随机数；中转帧引出来的回显那个帧里的前 8 个字节；"对端没挂在我这里""这条路走不通"回显会话握手时的随机数。路径之外的人猜不到这些，伪造来源地址发一个错误帧拆不掉别人的会话。回显对不上的"没有会话"只让节点马上发一个 PING 去问一下。
- 一个 relay 有几个地址时，INIT 同时发给每个地址，先回答 CHALLENGE 的那个承载这一次握手和之后的会话；会话断了，下一次又是每个地址一起试。
  回答了 CHALLENGE、握手却走不完的地址（地址和别的 relay 撞了，回答的是另一台机器）这一轮不再试，剩下的马上接着试。同一个地址是几个 relay 的时，
  收到的会话帧交给每一个，只有在等这个随机数的那个认它。本节点自己的地址不试。TCP 每隔 250 毫秒（前一个失败时马上）开始连下一个地址，
  先连上的为准；上一次握手成功的地址下一次排在最前。所以连不上的地址不让挂靠变慢，UDP 过不去的 relay 也不用谁说明，节点自己走 TCP。
- 走 TCP 的节点在 TCP 连接上做同样的握手，会话绑定在这条 TCP 连接上。握手要在连上之后 10 秒内完成，握手之前只收握手的帧；每个来源最多占 8 条还没有握手的连接。
- TCP 里的帧不会丢，只会迟到，所以节点在 TCP 上握手不重发，每一步等 4 秒：丢包的链路上 TCP 一次重传就是一两秒，照 UDP 的节奏（半秒重发、两秒放弃）握手会接连失败。保活连续没有回答时不等，照样拆掉重连：真实链路上量过，卡住的 TCP 多数等很久也不恢复，新拨一条通常不到 1 秒就握上手。
- relay 设了带宽上限时，各个来源节点公平地分：桶快空的时候，上一秒已经用掉自己那一份的来源先等着。
- 往 TCP 里写的两头都要限制积压：发送队列有上限（满了丢新来的包），内核里未发出的数据也有上限（`TCP_NOTSENT_LOWAT`）。
- 两头都给这条 TCP 设了重传定时器的上限（2 秒），同时设放弃的时限：节点这头 10 秒，比它自己判断这条 TCP 死了要等的都长；relay 那头 30 秒，就是会话的有效期。见 §8.3。

### 5.3 直连与探测

一个对端的直连地址要先验证过才能用：

```
A → B   PING  { A, B, 随机数, 签名 }
B → A   PONG  { B, A, 同一个随机数, B 看到的 A 的地址, 签名 }
```

- A 向 B 的某个候选地址发 PING，收到带着同一个随机数、签名正确的 PONG，这个地址才算 B 的已验证直连地址，A 才会往它发连接包。
- B 收到签名正确的 PING 时，把来源地址记为"可以收 A 的包的地址"，并且自己也向它发 PING 做反方向的验证。
- 只凭一个签名正确的 PING，来源地址只被信任 15 秒；本节点自己反方向探测得到回答之后才延长。签名的 PING 可以被人录下来换个来源地址重放，所以它单独不能长期占住一个地址。同一个地址被两个对端声称时，归正在用它的那个。
- PONG 里对端看到的本节点地址要对得上本节点已知的自己的地址，否则不算数：中间夹着一台替两边转发的机器时，这个地址是它的。
- 打洞就是双方在约定的时刻互相向对方的候选地址发 PING。
- 已经在用的直连地址每 5 秒探测一次；连续超时就判为不可用，改走 relay。

候选地址从这几处来，都要经过上面的验证才会用：

- 本机网卡上的地址，以及 relay 和 controller 看到的本节点的外部地址。
- 局域网发现：节点在本地网段上发组播信标，只有已经知道发送方公钥的节点认得出它。同一个局域网里的两个节点由此直接互连，这样的直连无条件优先。
- 端口映射：向路由器申请把节点的端口映射出去（UPnP-IGD、NAT-PMP、PCP），拿到的外部地址作为候选；节点退出时撤销。
- IPv6 地址。节点的端口在系统允许时同时收 IPv4 和 IPv6。

### 5.4 选路

`i3t-path` 为每个对端维护"现在走哪条路"。发包时只查这一个结果，不做别的判断。

- 默认模式：直连可用就走直连；否则经一个 relay。经 relay 时按这个顺序取第一个可用的：
  1. 对端自己就是 relay，并且本节点和它之间有中转会话：直接把包发给它（它收到目的是自己的包就交给连接层）。
  2. 本节点自己是 relay，并且对端在本节点上有会话：用这个会话。
  3. 对端挂靠的 relay，按对端到它们的延迟从低到高。

  前两条不经过第三台机器，所以排在前面。对端挂靠的 relay 之间，现在走着的那个只要没有明显变慢就不换：对端上报的顺序会随测量的起伏来回变。
- 延迟优先模式：列出直连和经 1 到 4 个 relay 的全部路径，按代价比较，取最低的。
  - 代价以毫秒计：各段延迟之和，加上抖动、丢包折算成的延迟，再加上 relay 的负载惩罚。本节点到 relay 的那一段是自己测的；relay 之间的各段来自 relay 发布的状态行；最后一段是对端上报的它到 relay 的延迟。
  - 换路有迟滞：新的路要连续 3 个评估窗口（每个 5 秒）都便宜至少 max(5 ms, 10%)，换过之后至少停留 30 秒。两条路来回换的时候停留期逐次加倍，最长 8 分钟。
  - 现在的路断了就立刻换到剩下的里面代价最低的，不等迟滞。
- 两种模式共同的规则：
  - 到一个 relay 的会话断了又连上之后，要保持满 30 秒，流量才会换回经它的路上。一条时好时坏的链路每次重连之后头几秒看起来总是好的，不这样流量会跟着它一断一连地来回换。从没断过的会话不用等；原来的路断了、只剩它能走的时候也不管这一条。
  - relay 通知自己即将下线或者过载时，节点立刻把路和挂靠挪到别的 relay 上；过载的 relay 恢复之后各节点各等一段随机的时间再回去。
  - relay 之间的一条连接要两头都报了才算数，延迟和丢包取两头里差的那个：一个 relay 不能把自己的连接报得比邻居量到的更好，把流量引到自己身上。
- 两条路对 `i3t-conn` 报同一个最大包长（`i3t-proto::MAX_CONN_PACKET_LEN`）。
- 没有任何路可走时，包被丢掉，连接自己在空闲超时之内等路恢复。路断着（或者对端一阵没有回音）的时候，路径层给每个对端留着最后发出的几个包：路回来、或者静默的对端又发来了包时，把它们再发一遍，两头的连接不用等各自退避到很久之后的重传（§8.3）。

### 5.5 连接

- `i3t-conn` 给每个对端一个固定的虚拟地址（由节点编号算出），QUIC 始终把对端看成这个地址。所以换路时 QUIC 不知道。
- 一对节点一条连接，按需建立，没有流之后按性能档位的时间关闭（默认 5 分钟，§8）；设为常驻的对端不关。
- 连接编号的校验密钥和"无状态重置"的密钥都从节点的私钥派生，重启之后不变。节点崩溃重启之后，对端在旧连接上发来的包会得到一个重置，对端立刻知道连接没了、重新拨号；否则要等 30 秒的空闲超时，这期间它开的新流都没有回音。
- 保活 15 秒，空闲超时 30 秒，并发流上限 16384，每条流的接收窗口默认 2 MB（这也是上限，见白皮书 §6.4；低占用档位 1 MB）。
- 连接的发送窗口默认 64 MB（低占用档位 16 MB）：流的优先级只能排已经交给连接的数据，窗口太小时几条大流量的流就能把它占满。
- 连接的接收窗口和发送窗口一样大：对端发过来、本端还没有读走的数据，一条连接上所有的流加起来不超过这么多。没有这个上限的话，任何一个对端都能开满流、压满每条流的窗口，把本端的内存吃光。
- 加密套件按 CPU 选：有 AES 指令的机器上 AES-GCM 排在前面，没有的排 ChaCha20-Poly1305；做服务端的一方没有 AES 指令时按自己的顺序挑，所以两边谁缺 AES 指令，这条连接就用 ChaCha20（§8.1）。
- 同一个对端最多同时有 2 条连接（两边同时拨号时会有两条）。再来第三条就关掉最老的：守规矩的对端只在手上的连接都不能用了才会重拨，所以最老的那条在它那边已经是死的。
- 进来的握手同时最多处理 64 个，每个对端 4 个。挤的时候，没有验证过来源地址的握手先被要求重试一次（QUIC Retry），伪造来源地址的握手到不了这一步。
- 拥塞控制在 `i3t-conn/src/congestion`，默认是一份按公开草案自己写的 BBR（环境变量 `I3T_CONGESTION=cubic` 可以换回 Cubic 做对比）。QUIC 库自带的 Cubic 把每次丢包都当作拥塞，在有随机丢包的长距离链路上很慢：50 ms、丢包 1% 的 100 Mbit/s 链路上只有 2.6 Mbit/s，BBR 是 87 Mbit/s。库自带的 BBR 带宽估计只升不降，不能用。测量的办法在 `bench/congestion`。

### 5.6 流

每条用户连接是 QUIC 连接上的一条双向流。流上的第一样东西是建流请求（`i3t-proto::flow`），后面直接跟数据：

```
发起方 → 对端   OPEN  { 目标, 服务等级, 来源说明 } 首批数据…
对端 → 发起方   REPLY { 状态, 说明 } 数据…
```

目标有四种：经对端访问互联网（域名或地址加端口）、对端自己的服务（端口）、对端所在局域网里的地址、下发给对端的某一条端口转发（编号）。

发起方是谁由连接的握手确定，流上不再认证。对端收到 OPEN 后按发起节点查访问规则，再按目标类型查自己的能力和出站策略。

接受流的一方在读 OPEN 之前先看发起节点：

- 没有任何一条访问规则允许它访问本节点的，流直接重置，一个字节也不读、不缓存。
- 同一个对端同时在处理的流超过 16384 条的，回"流太多"（状态 `0x27`），同样不读 OPEN。这个数和一条连接上并发流的上限一样，装得下一个网关经同一个出口挂着的几千个请求；它限制的是一个对端最多能占用多少文件描述符。

流没有空闲超时：一条不说话的 SSH 或数据库连接、一个正在等模型思考的请求都是正常的。流两头的每条 TCP（入口上客户端连进来的那条，出口上连目标的那条）都开内核保活，静默 25 秒开始探测。只有一头真的没了，流才会被拆掉。

节点失去一项能力（不再是出口、关了局域网访问、删了端口转发），或者访问规则不再允许某个对端时，靠这一项放行的、正在进行的流立刻被重置，不等它们自己结束。

出口替别人访问互联网时，除了私有、回环这些只在本地有意义的地址，也不去连本节点自己的地址（包括 relay 和 controller 看到的外部地址、路由器上映射出来的地址）和 netmap 里其他节点与 relay 的地址：不然关着"局域网访问"也能经路由器的公网地址摸到它的管理界面。域名解析同时最多 64 个，每个发起方 16 个。

绑定在非回环地址上的代理入口一律要求凭据，不管配置里有没有写。

乐观回复（白皮书 §8.1：入口不等对端的 REPLY 就告诉客户端连上了）先看监听器的设置，再看出口的设置（只管经那个出口出去的
互联网和局域网目标，netmap 里对端的 `exit.optimistic`），都没有时按目标的种类：互联网目标用，组网目标不用。监听器排在前面：
它是为这一个入口定的，出口的设置管的是经它出去的所有入口。

HTTP 代理入口除了 `CONNECT`，也转发明文 HTTP 的请求（`GET http://主机[:端口]/…`，`http_proxy` 指向它时就是这样）。凭据和出口
照旧来自 `Proxy-Authorization`，开的是同一种流（互联网目标，端口是 URL 里的，不写是 80，出口的端口白名单按它查），限额和计数也一样。
入口改写请求头：请求行只留路径，`Host` 换成 URL 里的，逐跳的头（`Connection`、`Keep-Alive`、`TE`、`Upgrade` 和 `Connection`
里点名的）和全部 `Proxy-*` 不往前传，加上 `Connection: close`。一条流只承载一个请求：目标回完应答关连接，入口随之关掉客户端的连接，
在同一条连接上排在后面的请求不发出去。请求体按 `Content-Length` 或 `chunked` 划界，只把这一个请求的请求体搬给目标；
请求体发完之后不关流的发送方向，等应答发完（有的服务器把半关闭当作客户端走了）。`Expect: 100-continue` 原样转给目标，它回的 100 原样回给客户端。
能让入口和目标对请求边界理解不一致的写法（`Content-Length` 和 `Transfer-Encoding` 同时出现、出现两次、`Connection` 点名了它们）回 400，
`chunked` 之外的编码和 `https://` 的地址回 501，请求头最长 32 KB。明文 HTTP 总是等对端的 REPLY 再往下走（监听器和出口的乐观回复对它不起作用）：
目标的应答本来就在 REPLY 之后才到，等它不多花时间，被拒绝时客户端拿到的是 403、502、504 这样的状态码。

端口转发的"目标连不上"（白皮书 §9.6）记在监听节点上：它开到目标节点的流被拒绝时，拒绝里的状态就是原因（连接被拒绝、超时、
不可达、目标节点没有这条转发、访问规则不允许），开不出流时是到目标节点不通。原因和时间随它的上报到 controller（端口转发的
`target_failure`），有一条流成功就清掉。监听在虚拟 IP 上的转发由监听节点的出口一侧接住，它连目标时的成败记在同一处。
UDP 的转发只看得到会话开不开得起来。

端口转发可以要求目标节点连上目标之后先发一个 PROXY protocol 的头（v1 或 v2，每条转发自己设，默认不发，只有 TCP）：
认它的服务据此看到发起节点的虚拟 IP。头里的来源只取自连接的握手认出的发起节点，建流请求里写的什么都不算。

每条流结束时，入口和出口各记一行摘要（`流结束`，info 级，不采样）：对端、目标的种类、服务等级、两个方向的字节数、首字节时间、
怎么结束的，以及这对节点的连接在流开始时和结束时走的路（`route_start`、`route_end`：`直连 地址`、`经 #3 → #5`、`不可达`）、
中间换没换过（`route_changed`，换过又换回来的也算）。不记目标地址。走独占 TCP 的流写的是这对节点共用连接的路，流层看不出底下是哪一种传输。

异常结束用流的重置来传递，不能表现成正常结束：目标一侧异常断开时，对端重置这条流，入口再用 RST 关掉客户端的连接。

### 5.7 UDP 应用的数据与服务等级

UDP 应用的数据（SOCKS5 的 UDP ASSOCIATE、UDP 端口转发）走"数据报上下文"：

- 发起方在一条流上发一个"开数据报上下文"的请求，对端应答之后，这条流就只代表这个上下文的存续：关掉或重置它，上下文就结束。
- 之后的数据报带着上下文的编号，走连接上不可靠的数据报通道。每个数据报自带目标地址，所以一个上下文在出口上对应一个 UDP 套接字，映射与目的地址无关。
- 数据报超过连接允许的大小时，在发送方分片、在接收方重组，重组的内存和时间都有上限。relay 看不到这些。
- 出口对每个目的地址做和流一样的访问规则与出站策略检查。
- 数量有上限：出口上每个对端最多 128 个上下文；一条 UDP 端口转发最多 64 个会话，每个来源地址（一个 IPv4 地址，或者一个 IPv6 的 /64）最多 16 个，本机回环来的不限。

服务等级决定同一条连接上谁先发：交互类的流优先级高，大流量的流让位；`auto`（默认）开始按交互类调度，累计超过 1 MB 之后降为大流量的优先级。等级写在代理用户名的后缀里（`+c-i`、`+c-r`、`+c-b`）。UDP 应用的数据在"不丢包优先"等级下每个数据报单独走一条流，路上不丢；其他等级走不可靠的数据报通道。

### 5.8 独占 TCP（lane）

默认情况下一对节点之间所有的流都在那一条 QUIC 连接里。这有两个代价：丢一个包，连接上不相干的流一起等；内容本身已经是 TLS 的流量还要在 QUIC 里再加密一次。对多数用法无所谓，对"入口和出口之间挂着几千条长时间的 HTTPS 流"（比如网关）就明显了。所以可以按节点对打开另一种传输：每条流独占一条 TCP 连接，叫 lane（`i3t-lane`）。它不是默认的，也不会被自动选中。

**设置。** 每对节点一项，三个取值：不用（默认）、UDP 不通时用、总是用。两个节点里至少有一个要启用为 relay（只有 relay 监听 TCP），否则设置不起作用，管理接口会说明原因。

**连接。**

- lane 由"连得上对方 TCP 端口"的那一方拨向对方的节点端口，也就是 relay 的 TCP 监听用的那个端口。进来的 TCP 按第一个字节分：`0x16`（TLS 握手记录）是 lane，其余的是 relay 的 TCP 接入（开头是 2 字节的长度，高位字节是 0）。
- 每条 lane 是一条 TLS 1.3 连接，两边按 netmap 里的节点公钥互相认证，和节点连 controller 的做法一样。认不出公钥的在握手里就被拒绝。
- 一条 lane 只给一条流用，用完就关，不复用。
- 拨号的一方提前把 lane 拨好、握完手放着：一部分留给自己发起的流，一部分停在对方那里，对方要向这边开流时取一条用。停着的数量跟着新建流的速率变（最多 64 条空闲，突发时一次补拨最多 512 条）。池空了的流最多等 2 秒，等不到就改走 QUIC 连接。
- 两边之间另有一条控制用的 lane：要求"再拨几条"、互相 ping、通知"我要下线了"。拨号方重启或者公网地址变了会换一个代数，对方立刻丢掉旧代数的空闲 lane：家宽重拨之后旧连接不会收到 RST，不这样就会取到死连接。
- 每条 lane 的 TCP 设了重传定时器的上限（2 秒）和放弃的时限（空闲 90 秒、开流之后等回话 15 秒、流里 120 秒）：一段完全不通过去之后，最多两秒就恢复，不用等加倍了的重传定时器（§8.3）。

**一条流。** 发起方在 lane 的 TLS 里发建流请求（和 QUIC 上的相同）和首批数据，对方回复之后：

- **加密模式**：流的字节一直走这条 lane 的 TLS。一个方向结束时先发 TLS 的关闭通知再关 TCP；没有通知就断了算异常结束。
- **透传模式**：首批数据本身是一个完整的 TLS ClientHello 时用。建流的请求和回复交换完之后，这条 TCP 退出 TLS，原样搬运用户的字节，Linux 上用 `splice` 在内核里搬。这些字节本来就是用户和目标之间的 TLS，所以不需要节点再加密；建流请求（里面有目标地址）仍然是加密的。
- 两种模式下，异常结束都以 TCP 的重置传到对面，不会变成正常结束。

**选哪种传输**由发起流的节点对每条流单独决定：只有承载 TCP 连接的流会走 lane，UDP 应用的数据、数据报上下文始终走 QUIC 连接。"UDP 不通时用"看的是这对节点的 QUIC 连接现在有没有 UDP 的路。开不出 lane（池空、对方拒绝、端口连不上）时，在发出任何数据之前悄悄改走 QUIC 连接，并计一次数。已经在跑的流不换传输。

访问规则、出口的配额、凭据的用量、每个对端的流数上限、排空，在 lane 上和在 QUIC 连接上是同一套代码、同样的行为。lane 上的流不随选路变化（它就是那一条 TCP），节点对之间的 QUIC 连接和它的路由照常保留。

本机实验环境里量到的（同一组网关负载，开和关）：入口和出口合计的 CPU 少三到五成；400 个请求同时到达、各带最多 1 MB 的请求体时，上传的中位数从 342 ms 降到 22 ms；往返 150 ms、丢包 1% 时，一次停顿牵连的流从最多 58 条降到最多 4 条，但每条流要自己握手和慢启动，首字节的中位数从 355 ms 涨到 934 ms。

### 5.9 主动测试

节点平时量到的只有它正在用的路。管理员想知道"这两个节点能不能直连、直连和经某个 relay 各是什么质量"时，可以对任意一对节点发起一次主动测试（`i3tctl test <a> <b>`，接口见 [admin-api.md](admin-api.md) §19）。四个项目：

| 项目 | 做什么 | 结果 |
|---|---|---|
| 直连能力 | 两个节点按 §5.3 试一次直连，不管选路会不会用它 | 成不成、哪一种、用了多久、不成的原因 |
| 直连质量 | 在直连上发一列探测（100 个，间隔 20 ms） | 延迟的最小、平均、95 分位，抖动，上行和下行各自的丢包 |
| relay 质量 | 同样的一列探测，强制经指定的 relay 或多跳路径 | 同上，加上每一跳各占多少延迟 |
| 路由决定 | 用刚量到的数算 | 两种选路模式各会选哪条路、为什么。延迟优先模式从这一对现在走的路出发、用选路器自己的差距（§5.4 的 max(5 ms, 10%)）算：更便宜的候选便宜得不够时，选的还是现在的路，那条更便宜的和两边的代价一起给出 |

relay 质量默认量两条路径：默认模式会选的和"成本最低"模式会选的；也可以点名（`--via`，最多两条）。吞吐要单独要求（`--throughput`）：每条路径每个方向一条测量流，5 秒或者 20 MB 先到为止。全网矩阵对所有节点对分批做直连能力和延迟，同时最多四对，不量吞吐。

**怎么进行。** controller 通过节点的控制连接给两端同一个测试编号和时间窗，一端发起、一端配合，各自上报，controller 合并成一份结果，每对节点留最近 20 次。

- **探测**是签了名的 TPING / TPONG（探测帧的第 `0x0f`、`0x10` 种），带着测试编号和它自称走的路径。回答从同一条路径倒着走回去，并且不比探测大。
- **测量流**是共用连接上的一种流（建流请求的第 `0x03` 种）：对端要么只收，要么发回指定数量的字节，结束时报告它那一侧搬了多少。它的优先级最低，不走 lane，不算出口的流量。速率由收的一侧数，不算开头的四分之一：连接刚开始发的时候速率是从很低爬上来的，算进去的话先量的那条路径会比后量的低一截。
- **暂时固定路。** 吞吐要量指定的路径，就得让这对节点的连接在测试的几秒里真的走那条路。路径层给这个对端加一个"固定"：选路规则照常算、照常记，只是结果被固定的路径盖住；固定最长 30 秒，持有它的任务结束或者被取消时立刻解除，然后回到规则选的路。固定直连只会用已经通着的直连，不会因此打开一条规则不用的直连。这几秒里这对节点之间别的流量也走这条路，结果里写明了。

**节点自己守的规矩**，不依赖 controller：

- 只回答 controller 打开的测试里、那个对端发来的探测和测量流，过了时间窗就不认。对端自己开不了测试。
- 只经 relay 的节点不试直连、不回答直连的探测，所以测试不会让它暴露地址；只用直连的节点不测经 relay 的路径。
- 吞吐测试可以在本机关掉（配置文件 `[tests] throughput = false`，或者 `i3t set throughput-tests off`），延迟和直连的测试照常。
- 上限在本机：同时最多 8 个测试；和同一个对端两次测试至少隔 8 秒，带吞吐的至少隔 25 秒；时间窗最长 150 秒；每条测量流 20 MB、5 秒，一个测试最多 6 条、同时一条；一个测试最多回答 500 个探测。
- 访问规则只对正在做吞吐测试的那个对端的测量流放行，它开来的别的流照旧被拒绝。

结果是一次快照，里面写明了量它的传输、拥塞控制和时长。定时重复测试没有做。

### 5.10 透明访问（Linux）

本机的程序不配代理，直接连别的节点的虚拟 IP（或者 `<名字>.<网络的域名>`）和端口：`ssh 10.66.0.5`、`curl http://nas.home.i3t:8080`。
没有虚拟网卡，也不在程序里逐包处理：拦截发生在建立连接的那一刻，由内核的包过滤规则做，之后应用的连接和本机入口之间是一条普通的回环连接，
节点照常把它当成一条流运走（白皮书 §9.5）。

**开关。** 默认关。只能在本机打开：`i3t set intercept on`（`config.toml` 的 `[intercept] enabled`），重启 i3t 生效；它改这台机器的网络配置，
controller 没有开关。节点进程要有 `CAP_NET_ADMIN` 和 `CAP_NET_BIND_SERVICE`（root 都有；以 `i3t` 用户跑的系统服务装上
`deploy/systemd/i3t.service.d/intercept.conf`，单元文件的沙箱设置不用放开），系统里要有 `nft`（nftables）和 `ip`（iproute2）。缺什么，节点在上报和 `i3t intercept status` 里用代码说出来
（[admin-api.md](admin-api.md) 第 5 节的 `intercept`），代理和端口转发照常。只有 Linux 有；别的平台上配置照收，状态是"这个平台上没有"。

**装进系统里的**（`i3t-intercept`；节点启动时装，停下时拆，`i3t intercept status` 列出来）：

| 东西 | 做什么 |
|---|---|
| nftables 的表 `ip i3t`，集合 `peers` 里是本节点能访问的对端的虚拟 IP | `intercept`（`output` 的 NAT）：发往 `peers` 的 TCP 连接改到 `127.0.0.1:1`，入口用 `SO_ORIGINAL_DST` 取回原目标。`refuse`：发往地址段里别的地址（不是节点、访问规则不允许的节点；本节点自己的虚拟 IP 除外）的 TCP 当场回 RST，UDP 当场失败；别的协议（比如 ping，连发往对端的也算）当场回 ICMP 的"被管理员禁止"，发往地址段的包一个也不从真网卡出去。`reroute`（`output` 的路由链）：发往 `peers` 的 UDP 打上标记 `0x20000000`；本节点带标记的连接，对方回的包按连接跟踪也打上标记。`divert`（`prerouting`）：带标记、经回环绕回来的 UDP 用 TPROXY 交给 `127.0.0.1:1`。`guard`（`prerouting`）：从真网卡进来、却自称来自网络地址段的包丢掉 |
| 策略路由 `2033: fwmark 0x20000000/0x20000000 lookup 2033 proto 203`，表 2033 里 `local default dev lo proto 203` | 带标记的包在本机投递：绕回来的 UDP，和目标一侧服务回给本节点的包（见下） |
| dummy 网卡 `i3t0`（别名 `ice3tier`），上面只有本节点的虚拟 IP（/32） | 本节点自己的虚拟 IP 在本机可达；名字服务听在它的 53 端口上；systemd-resolved 按这块网卡分域名 |
| systemd-resolved 在 `i3t0` 上的设置（有它时）：DNS 是本节点的虚拟 IP，路由域 `~<域名>`，不是默认路线 | 只有网络的域名下的查询发给节点；只在内存里，网卡一删就没了 |

每一样都认得出是自己的（表名、规则和路由的 `proto 203`、网卡的别名），别的东西一概不碰：路由表 2033 里有别人的路由、或者有一块不是自己建的
`i3t0` 时不装，说明是谁挡着。网络的地址段和这台机器所在的真实网络重叠时也不装（`range_in_use`，说出重叠的是哪个地址或者路由）：
本机网卡上（`i3t0` 之外）有地址段里的地址，或者 `main` 表里有一条和地址段重叠的路由（默认路由、把默认路由拆成两半的 `0.0.0.0/1` 和 `128.0.0.0/1`、经 `i3t0` 的不算）。查不清的时候（读不懂系统的回答）也不装。
装上会把它从那个网络上切下来（`guard` 丢掉那个网络进来的包，`refuse` 拒绝发往它的包），远程的服务器连自己的 SSH 会话都会断；
这时上次留下的自己的东西也拆掉。装之前查，地址段变了重装时再查；装着的时候每 5 秒再查一次（两个 `ip` 命令）：机器后来才进了一个重叠的网络
（DHCP 换了地址、VPN 连上），当场全部拆掉，状态是 `failed`、`range_in_use`；因为重叠没装的也照样每 5 秒查，重叠没了自己装上，不用重启节点。
某一次查不清时什么也不改。表在一个 nft 事务里整个替换，规则保证正好一条，网卡沿用、地址换成现在的：进程被杀掉留下的东西下次启动时被认出来、
换掉，不会多一份；关着启动、或者节点没运行时 `i3t set intercept off`，有权限就把留下的拆掉。中途哪一步失败，已经装上的全部拆掉。
能访问的对端变了只换 `peers`（一个事务），本节点的虚拟 IP、地址段或者域名变了整个重装。

**一条 TCP 连接。** 被改到入口的连接按原目标找到那个对端，开一条 `Target::Node`（那个端口）的流，和本机 SOCKS5 入口访问 `<虚拟 IP>:<端口>`
开的流一样，在对端按同样的访问规则、每对端上限处理；计数单独记一路（`intercept` 的 `active`、流量），也算进节点的流量和流数。
应用的 `connect()` 在本机入口那里就成功了，之后的失败只能是重置，所以它和端口转发一样不等对端的 REPLY：首批数据（最多等 50 毫秒）随 OPEN 发出，
对端拒绝时 RST。不是节点的地址、访问规则不允许的节点在内核里当场被拒绝，应用得到"连接被拒绝"；对端没开的端口是"连上之后马上被重置"，
做不到"连接被拒绝"：那要等问过对端才完成和应用的握手，内核不提供。本机入口还按当前的 netmap 再核对一次原目标（集合还没换的一瞬间、
有人直接连入口的端口时原目标是入口自己），对不上就重置。

**UDP。** 发往对端的报文在 `output` 打上标记，策略路由让它经回环绕回来，`prerouting` 的 TPROXY 交给入口的透明 UDP 套接字，每个报文带着原目标
（`IP_ORIGDSTADDR`）。会话按（应用的地址，原目标）分，各是到那个对端的一个数据报上下文，目标是 `Target::Node`；回给应用的报文从一个绑在原目标上、
连着应用的透明套接字发出，来源就是应用发往的地址，内核之后把这个应用发往同一个目标的报文直接交给它。同时最多 64 个会话，空闲 60 秒回收。

**目标一侧。** 透明访问打开着时，别的节点开过来的流连本机的服务，用发起节点的虚拟 IP 做源地址（`IP_TRANSPARENT`，绑定那个地址），套接字带标记；
服务回的包按连接跟踪打上同样的标记，经策略路由在本机投递回来。所以服务的日志和按地址的访问控制看到的是对端。这个地址只取自连接的握手认出的发起节点，
建流请求里写的什么都不算；`guard` 让别的机器冒充不了网络地址段里的来源；本机的普通用户绑不了别人的虚拟 IP（要 `CAP_NET_ADMIN`）。
只对本机网卡上的非回环地址这样做：内核不肯把源地址是回环地址的包发往别处，回环上的服务回不了包，所以指向 `127.0.0.1` 的端口转发照旧是 `127.0.0.1`；
UDP 照旧用本机的地址（一个数据报上下文的套接字同时发往互联网、局域网和本机，绑在对端的虚拟 IP 上就只能发往本机）。关着时和以前一样。

**名字。** 节点在自己虚拟 IP 的 53 端口上答 `<名字>.<域名>`：本节点能访问的对端和自己的 A 记录（TTL 30 秒），域名下没有的名字 NXDOMAIN，
别的名字 REFUSED，不是这台机器的解析器。有 systemd-resolved 时（常见的发行版），它在 `i3t0` 上只把这个域名路由过来，`ssh nas.home.i3t` 直接能用；
没有时 `i3t hosts` 打印 `/etc/hosts` 的一段，`i3t hosts --apply` 写进去（前后有标记，只换上次写的那一段），`i3t hosts --remove` 只去掉那一段，
文件别的字节不动。这一段不随透明访问拆掉；透明访问关着、它还在时，`i3t intercept status` 和 `i3t set intercept off` 说出来，指出 `i3t hosts --remove`：
没有拦截时这些名字指向的地址走默认路由。只有全名，短名字可能是局域网里的另一台机器。

**节点自己的连接不绕回来。** 节点不把覆盖网的地址当普通地址去连：写了这种地址的端口转发、解析成这种地址的域名直接拒绝（不管透明访问开没开）；
本节点带标记的连接也被拦截规则跳过。

**谁能用。** 本机（这个网络命名空间里）的任何程序、任何用户，和回环上不要凭据的代理入口一样：它们得到的就是这个节点的访问权限。
别的网络命名空间（桥接网络的容器）里的程序不经过这些规则，它们发往虚拟 IP 的包照旧走默认路由；用主机网络的容器和本机一样。入口在 `127.0.0.1:1`，
低端口普通用户绑不了：节点崩溃之后规则还在的那段时间里，别的用户也抢不到它。

**IPv6。** 网络的地址段和虚拟 IP 只有 IPv4（`Network::cidr`、`Peer::virtual_ip`），没有 IPv6 的覆盖网地址可以拦截，没有做。

**前提。** 要有一条覆盖网络地址段的路由（默认路由就是）：内核在拦截规则之前先查路由，查不到时 `connect()` 直接"网络不可达"。

**量到的**（本机实验环境，直连；入口一侧的程序用 Python 的套接字下载，每种三次）：

| | 不限速：1 条流 / 16 条流（Gbit/s） | 入口 / 目标每 GB 的 CPU（秒，1 条流） | 千兆、往返 10ms：1 / 16 条流（Mbit/s） | 建连到第一个字节（ms，不限速 / 千兆） |
|---|---|---|---|---|
| 本机 SOCKS5 入口 | 6.6 / 7.3 | 1.27 / 1.17 | 920 / 919 | 0.72 / 20.8 |
| 端口转发 | 6.8 / 7.4 | 1.24 / 1.11 | 920 / 919 | 0.62 / 10.7 |
| 透明访问 | 6.9 / 7.4 | 1.26 / 1.10 | 921 / 920 | 0.64 / 10.6 |
| 透明访问，目标一侧也开着 | 6.5 / 7.5 | 1.30 / 1.18 | 920 / 919 | 0.64 / 10.7 |

吞吐和 CPU 在起伏之内一样：透明访问没有量得出的吞吐损失。建连和端口转发一样是一个往返；SOCKS5 入口访问组网目标要先等对端的 REPLY 才告诉客户端
连上了，多一个往返。内核里的重定向本身量不出代价，见 8.4 的 eBPF。

### 5.11 出口测试和 ping

两个运维命令（白皮书 §13），都只读手上现成的东西或者做一次很小的尝试，不能拿来扫描：

- **`i3tctl exit test <出口> <主机[:端口]>`**（管理接口 `POST …/exits/{node}/test`，见 [admin-api.md](admin-api.md) 第 17 节）：controller 给出口节点发
  一条 `exit_test`，节点按它替别人连这个目标时的同一套规矩做（`i3t_exit::Outbound::probe`：写成地址的私有地址按局域网目标查，别的按互联网目标查；
  不是出口、端口不在白名单里、解析出来的地址不该连都拒绝，原因的代码和别人经它访问时被拒绝的一样），记下解析（不用缓存，量它花了多久）、
  连接、端口是 443 时的 TLS 握手（不检查证书，只看能不能握完、多久）各花多久、卡在哪一步、经不经上游代理，用 `exit_test_answer` 送回。
  节点自己限制：一次一个，两次至少隔 2 秒，每一步最多 5 秒。目标要管理员给，没有默认的目标。比它旧的节点跳过这条消息，回答是"没有回答"。
- **`i3t ping <节点>`**：本机的命令经本机状态接口（`/ping`，要状态目录里的令牌）让正在运行的节点在到那个节点的连接上量几个往返（默认 5 个，
  最多 10 个，8 秒之内做完，一次一个）。每个往返是连接上新开的一条流，第一样东西是"往返测量"的 OPEN（`i3t-proto` 的第 `0x04` 种，两个字节），
  对端读到就回一个成功的 REPLY：它照常先按访问规则和每个对端的流数上限筛，所以访问规则不允许时拿到的是拒绝。到对端还没有连接时，
  先量的那一个把连接建起来、不算数。结果是最短、平均、最长、丢了几个，和这段时间开始、结束时这对节点的连接走的路：经 relay 的写 relay 的名字，
  两条不一样才写成"开始 → 结束"（中间换过又换回来的不算，那种来回记在流日志的 `route_changed` 里）。本节点的配置里没有那个节点、
  访问规则只允许它访问本节点、它不在线、它的版本太旧不认这种 OPEN（它用协议错误重置流），各有一句明白话。节点协议没有为它升版：旧的对端只是不回答。

## 6. 节点更新

节点程序可以自己更新（`i3t-update`，发布流程见 [releasing.md](releasing.md)）：

- 一个发布是一组文件加一份清单，清单用发布私钥签名。节点只信任编译在程序里的公钥，运行时不能增加或替换。
- controller 定期查看发布源（默认是项目的 GitHub Release，可以换成镜像或本地目录），验过签名之后把用得到的包下载一次并缓存。节点不直接连发布源，经到 controller 的那条长连接分块取包，断了可以续传。
- 节点上的步骤：验签、只接受比自己新的版本、核对大小和哈希、运行新程序的自检、原子替换并保留旧程序、重启。新程序连上 controller 才算成功；启动了 3 次或者过了 5 分钟还没连上，节点自己换回旧程序，这个版本不再自动重试。
- 自动更新只在节点没有活跃的流时进行；管理员可以强制立刻更新，或者让节点排空之后更新。relay 一个一个更新。有节点因为版本本身的问题失败时，这个版本在它所在的那个网络里暂停自动更新，等管理员处理；只有 controller 确实让这个节点装过这个版本，它报的失败才算数，免得随便一个节点谎报就能让大家都不更新。
- 排空期间节点不接新的流，入口和出口都会给出明确的拒绝，手上的流照常结束。

## 8. 性能

这一章的规矩是先量再做：一样东西只有本机实验环境里量出了它带来什么，才进代码；量不出差别的写下"评估过、没有做"和那个数。
方法和全部的原始数在内部的测量记录里，这里是结论。测量都在 `tests/e2e/lab.py` 的网络命名空间里、用 release 程序做，机器是
14 核的 x86（有 AES 指令），同时还有别的构建在跑，单个数有一成上下的起伏。

### 8.1 性能档位

三个预设，每一项都可以在节点的 `config.toml` 的 `[performance]` 里单独改：

| 项（配置文件里的键） | low-footprint（低占用） | balanced（默认） | high-throughput（高速度） | 什么时候生效 |
|---|---|---|---|---|
| 工作线程 `threads` | 1（单线程的运行时） | 2 | 4 | 重启之后 |
| 每条流每个方向的搬运缓冲 `stream_buffer_kb` | 4 | 16 | 16 | 之后开始的流 |
| 每条流的接收窗口 `stream_window_kb` | 1024 | 2048 | 2048 | 之后建立的连接 |
| 连接的收发窗口 `connection_window_mb` | 16 | 64 | 64 | 之后建立的连接 |
| 没有流之后多久关闭连接 `idle_close_secs`（0 是不关） | 60 | 300 | 0 | 立刻 |
| 每分钟把空着的内存还给系统 `return_memory` | 是 | 否 | 否 | 立刻 |

线程数都不超过机器的核数。档位从哪里来：管理员在 controller 上给这个节点选了（`PATCH …/nodes/{node}` 的 `profile`，
`i3tctl node set <节点> --profile …`，经节点的 netmap 下发）就用它；没有选时用本机配置文件里的 `profile`（`i3t set profile …`），
默认 balanced。本机配置文件里单独写了的项总是盖过档位，因为它说的是这台机器自己的事。节点在上报里说它实际在用的档位、
工作线程数、哪些项被本机改了，以及换了档位之后线程数是不是还要等重启（节点详情的 `performance`）。旧的节点不认这个字段，
照旧按自己的配置跑。

每一项的依据：

- **线程。** 一条连接的包和它上面的流在几个任务之间互相唤醒；多一个工作线程就多一份跨核的唤醒和锁的争用。只有一个对端在忙时，
  一个线程最快也最省：满速 10.2 Gbit/s、入口和出口每 GB 各 0.7 秒 CPU；两个线程 6.9 Gbit/s、1.2 秒；四个 4.3 Gbit/s、2.2 秒；
  全部 14 个核（以前的做法）4.4 Gbit/s、2.2 秒。几个对端同时在忙时线程多才有用：四个入口经同一个出口，出口一个线程合计
  9.1 Gbit/s，两个 15.1，四个 22.6，十四个 18.4；八个入口时四个线程 23.1、十四个 23.7。relay 转发是在收包的那一个任务里做完的，
  线程多只多出唤醒：四对节点经同一个 relay，一个线程 23 Gbit/s、每 GB 0.24 秒，十四个 16.5 Gbit/s、0.40 秒。
  所以只有一个对端在忙的机器和纯粹的 relay 写 `threads = 1` 最快；档位不知道会有几个对端同时在忙，取了 1、2、4。
- **搬运缓冲**是每条流活着的时候一直占着的两块内存：2000 条开着的流，一个线程时 4KB 比 16KB 入口和出口各少约 45MB，代价是满速时每 GB 多两成 CPU。
- **窗口**是上限，不是预先占的内存，平时量不出差别；对端不读的时候它决定本端最多压住多少：往一个不读数据的目标上传 16 条流，
  2MB / 64MB 时出口多占 39MB，1MB / 16MB 时 18MB。流窗口在任何档位都不超过 2MB（QUIC 库的限制，白皮书 §6.4），16 条流也到不了
  64MB 的连接窗口，所以高速度档位把它调大量不出差别，没有调。代价是单条流不超过"流窗口 ÷ 往返时间"：1MB、往返 50ms 时约 170 Mbit/s。
- **空闲回收**：一条空着的连接占 1.3MB 到 2.6MB。高速度档位不回收，常用的对端开新流省一次握手（见下面的首字节时间）。
- **归还内存**：glibc 释放的内存多半留在进程里；每分钟让它把整页空着的还回去，空闲的入口再少 2.4MB 左右。忙的时候还回去的页
  马上又要重新要，所以只在低占用档位开。

不分档位、对所有节点都一样的：

- UDP 的分段卸载和批量收发一直开着。关掉（逐个收发）只省 2MB 内存，每 GB 的 CPU 却翻倍（0.73 → 1.41 秒，千兆链路上 2.07 → 4.79），
  对一个核的小机器正是错的取舍。
- 加密套件按 CPU 选（§5.5）：有 AES 指令的这台机器上 AES-GCM 每 GB 0.67 秒，ChaCha20-Poly1305 1.02 秒、吞吐低三分之一，
  所以低占用档位也不强制用 ChaCha20。没有 AES 指令的 CPU 上 ChaCha20 快得多，这里没有这样的机器，量不了。
- glibc 分配器的两个阈值固定在 128KB（大块的分配用完就还），空闲的节点少 1 到 1.6MB，满速搬运量不出 CPU 的差别。
- UDP 端口的收发缓冲 4MB：满速 10 Gbit/s 时一个包也不溢出；256KB 时每 8 秒丢两三千个包，内存（内核的）也不算在进程里。
- 探测的周期：15 秒和 5 秒空闲时的 CPU 一样（3 分钟 0.19 秒，主要花在 50ms 一次的定时器上），只是少发三分之二的探测包，
  却让空闲的路上的故障晚三倍才发现，所以不跟档位走。

### 8.2 量到的数

每个档位都是用它的预设值量的（各项不单独改），四个节点都在同一个档位。

| | low-footprint | balanced | high-throughput |
|---|---|---|---|
| 空闲 10 分钟后的常驻内存：普通节点 / relay / 入口 / 出口（MB） | 13.2 / 13.0 / 14.4 / 14.1 | 13.5 / 13.4 / 16.1 / 17.4 | 13.4 / 13.5 / 19.9 / 21.6 |
| 2000 条开着的流：入口 / 出口（MB） | 68 / 49 | 85 / 67 | 87 / 69 |
| 直连、不限速：1 条流 / 16 条流（Gbit/s） | 6.7 / 6.2 | 7.1 / 7.7 | 4.5 / 6.1 |
| 每 GB 的 CPU，入口 / 出口（秒，直连、不限速、1 条流） | 0.99 / 0.86 | 1.21 / 1.11 | 2.16 / 1.88 |
| 千兆、往返 10ms：1 条流 / 16 条流（Mbit/s） | 726 / 912 | 933 / 919 | 920 / 920 |
| 经 relay、不限速：1 条流 / 16 条流（Gbit/s） | 6.1 / 6.0 | 6.7 / 7.5 | 3.5 / 4.9 |
| relay 转发每 GB 的 CPU（秒，不限速 / 千兆） | 0.47–0.53 / 1.2–1.5 | 0.51–0.56 / 1.2–1.5 | 0.73–0.84 / 1.1–1.6 |
| 首字节（往返 20ms）：已有连接上新开的流 p50 / p99；新连接上的第一条流；空闲 70 秒之后（ms） | 20.9 / 22.0；46；46 | 21.0 / 23.1；47；22 | 21.0 / 23.3；46；22 |

怎么读：

- 每个数里大约有 10MB 是程序自己被映射进来的那部分（程序文件 22MB）；一个空闲节点自己分配的内存只有 2MB 左右。低占用档位
  达到了白皮书的目标（空闲 15MB 以内），刚满速下载过的入口和出口也是。
- 所以空闲内存再往下靠的是程序的体积，不是档位。发给用户的程序用构建档位 `dist`（根目录 `Cargo.toml`：整个程序一起做链接期优化、
  一个代码生成单元），表里的数是用普通的 `release` 构建量的：`dist` 构建的空闲节点在实验环境里从 14.3MB 降到 11.9MB，吞吐和每 GB 的
  CPU 不变。真机上（经老 glibc 的交叉构建，程序文件 15.1MB → 12.5MB）每个节点少 1 到 1.3MB，低占用档位的节点是 13 到 14.2MB。
  偏体积的优化量过，再少 1.4MB、每 GB 的 CPU 多一成，没有用。`release` 不带这些：那样每次测试构建都要慢近三倍。
- 端点的每 GB CPU 里包括了两头的 TCP（客户端到入口、出口到目标），不只是 QUIC。白皮书的目标（端点 1.5 秒、relay 1.5 秒）
  在不限速的链路上低占用和默认都达到了；千兆链路上的数偏高，一部分是 netem 限速的开销被记在了发送的进程上。
- 低占用档位千兆链路上单条流 726 Mbit/s：1MB 的流窗口在往返 10ms 时最多约 840 Mbit/s，往返更长时更低。
- 高速度档位在只有一个对端在忙时反而最慢（四个工作线程的代价，见 §8.1），它是给几个对端同时在忙的机器的：四个对端经同一个出口时
  它到 23 Gbit/s，默认 15，低占用 9。
- 高速度档位不回收空闲的连接，空闲之后的第一条流和已有连接上一样快；低占用档位一分钟就关，之后的第一条流要重新握手（多一个往返）。

### 8.3 断网之后的恢复

一条 TCP 遇到一段完全不通，内核每重传一次就把重传定时器加倍，路通了之后要等下一次重传才发现，平均要再等断开时长的一半；
跨境的丢包链路上 15 到 30 秒的断开并不少见。节点给自己开的、节点之间的 TCP（lane，到 relay 的 TCP 中转，两头）设两项
（`i3t_underlay::tcp_recovery`）：

- 重传定时器的上限 `TCP_RTO_MAX_MS`，2 秒（Linux 6.15 起才有，内核没有时两项都不设，和以前一样）；
- 同时设放弃的时限 `TCP_USER_TIMEOUT`。只设上限会出事：内核按重传的次数放弃连接，上限低了次数很快用完，1 秒的上限
  在 20 秒的断开里就把连接判死了。有了放弃时限，内核按时间放弃。时限按上面那一层的规矩定，TCP 既不先于它把连接判死，
  也不在它换掉这条连接之后还留着：lane 是原来的那几个（空闲 90 秒、等回话 15 秒、流里 120 秒）；节点到 relay 的 TCP 是 10 秒，
  节点自己保活连续三次没有回答（几秒）就换一条；relay 那头是 30 秒，就是会话的有效期。

`i3t tune` 说明这个内核支不支持。

两个机制要一起看。到 relay 的 TCP 断了之后节点会换一条；可这期间两头的 QUIC 连接也在退避，发数据的那一头被拥塞窗口卡着，
连收到的包都不确认，等它自己的下一次重传可能要几十秒，对端的连接先 30 秒空闲超时了。所以路径层在路回来时补发留着的包之外，
现在还在"静默了一秒以上的对端又发来了包"时补发（§5.4）：那一头收到对端补发的包，自己留着的包也马上补发出去，两头的丢包检测
都立刻恢复。

本机实验环境里量的（`tests/e2e/test_recovery.py`，那一段往返 100ms，netem 100% 丢包，流是经出口每 10ms 收一个小消息）：

| | 断开 20 秒 | 断开 40 秒 |
|---|---|---|
| lane，设了上限（2 秒） | 1.0、1.0 秒后恢复 | 1.5、1.4 秒后恢复 |
| lane，没设（几次的结果） | 0.4、0.6、0.6、0.7、19.1 秒 | 0.2、0.4、0.6 秒，一次 20 秒之内没有恢复 |
| 经 TCP 中转的共用连接，设了 | 2.9 秒后恢复 | 连接在 30 秒的空闲超时上结束，流以重置结束 |
| 经 TCP 中转的共用连接，没设 | 2.8 秒后恢复 | 同上 |
| 经 TCP 中转的共用连接，补发之前（设没设都一样） | 流断了：发数据的一头一直不确认，对端 30 秒空闲超时 | 同上 |

没设上限时恢复得快慢全看运气：路通的时候正好赶上一次重传就快，赶不上就要等到下一次，那时定时器已经加倍到十几、几十秒。
设了之后每次都在上限之内。经 TCP 中转的那一段，节点几秒之内就换了一条新的 TCP，恢复要等的是重连（断开期间连不上，退避到最长
4 秒），和这两项无关；断开超过 30 秒时，共用的连接按它的空闲超时结束，这是 §5.5 的规矩，要更长就得把空闲超时调长，没有调。

上限取 2 秒而不是 1 秒：两种上限下 lane 都在两秒之内恢复（1 秒时 0.6、0.7 秒和 0.1、0.2 秒）；可上限低于一条路本来要的重传时间时（往返长、抖得厉害的
跨境链路上常常过 1 秒），内核会在确认还在路上的时候就超时重传、把发送窗口收到最小。往返 600ms、抖动 120ms、丢包 0.5% 的路上
下载两次 5MB：1 秒的上限超时重传 4 次和 15 次，2 秒 7 次和 4 次，不设 2 次和 6 次。样本少、起伏大，但方向是上限越低误判越多，
多等一秒的恢复换这一份余量。

### 8.4 评估过、没有做的

- **别的分配器**：mimalloc 每 GB 的 CPU 和系统的分配器量不出差别（0.69 对 0.70 秒），空闲的常驻内存却多 10 到 12MB
  （一个线程时入口 29MB 对 19MB，relay 26MB 对 14MB）。不用。
- **每核一个运行时、`SO_REUSEPORT` 分流**：跨核的代价是真的（见线程那一条），可一个节点只有一个 QUIC 端点、一张路径表、一份
  relay 的会话表，按核拆开是重新设计；一个线程已经是单条连接最快的做法，几个对端同时忙时四个线程的多线程运行时到 23 Gbit/s。没有做。
- **绑核**：只有每核一个运行时时才有意义，没有做。
- **io_uring**：它要替换的是批量收发加分段卸载的那条路，这条路一个核已经搬 10 Gbit/s；白皮书自己也说零拷贝发送只对大块的发送有用。没有试。
- **XDP**：只对 relay 有用，而 relay 在这里转发 23 Gbit/s 只用 0.7 个核，瓶颈在两端（每 GB 各 0.7 秒）。没有试。
- **透明访问用 eBPF**（白皮书 §9.5 的设想：`connect()` 时改写目标，回退方案才是 nftables）：eBPF 改写之后应用的连接就是一条直接连本机入口的回环连接，
  它能达到的就是"直接连"。一个命名空间里量：没有任何 nft 规则（也就没有连接跟踪）直接连、装着 nft 的表直接连、经 nft 重定向，
  1 条流 23.3、23.1、23.5 Gbit/s，16 条流 176、178、177 Gbit/s，每 GB 的 CPU 一样，建连 0.274、0.281、0.274 ms。量不出差别，
  却要 BPF 的编译工具链或者签进仓库的目标文件、一个加载器、`CAP_BPF` 和 cgroup v2，命名空间的实验环境里也测不了。没有做。
- **一条连接上并发流的上限调低**：1024 比 16384 每条连接少 1.3MB，但会把一个对端同时开的流卡在 1024 条，比安全上的每对端上限和
  网关的两千条都低。低占用档位改为早一点关空闲的连接。
