# LLM 网关负载工具

复现"LLM API 网关经 ice3tier 出口访问上游"的流量，用来检查和测量节点在这种负载下的表现。

网关程序跑在一个节点（入口）旁边，把每个上游 API 请求经这个节点的本机代理入口（SOCKS5 或 HTTP CONNECT）发出去，代理的用户名写出口节点，请求从出口节点的网络到达 API。这类流量的特点：

- 请求体几十 KB 到 1 MB（提示词），之后是流式的小块回答；
- SSE：请求之后模型思考，几十秒到几分钟一个字节都没有（难的情况），或者每 10～15 秒一个保活注释（容易的情况），然后每秒 20 到几百个事件，中途可能停顿（调用工具），最后一个终止事件；
- WebSocket（实时类 API）：长时间的双向会话，服务端在输出时客户端还在发消息，两边都 ping，语音那样两个方向按固定节拍发二进制帧，两轮之间长时间空闲；
- 一对入口—出口上同时几百到几千条这样的流，匀速到达或者成批到达；
- 被截断的回答不能看起来像正常结束：上游中途出错时，客户端必须看到错误；
- 用户感受到的是首字节时间和事件之间的间隔，一条慢的流不能拖住别的流。

一个可执行文件 `i3t-llmgw`，两个子命令：

| 子命令 | 作用 |
|---|---|
| `upstream` | 模拟的 LLM API：HTTPS 和明文 HTTP 各一个端口，自己生成测试 CA 和证书。SSE 端点和 WebSocket 端点，每个请求怎么回答由请求自己说 |
| `load` | 扮演网关：按场景文件经代理（或者直连，作为对照）发流，逐条验证，测量，输出 JSON 和一张表 |

每个事件带序号、上游写出它的时刻和一个累积哈希（把它和前面所有事件串起来），负载端据此证明顺序、完整性、没有被改过，并算出每个事件路上多等了多久。提示词带着自己的哈希，上游核对它是否完整到达。

## 构建

```sh
cargo build --release -p i3t-llmgw
cargo test -p i3t-llmgw
```

## 上游

```sh
i3t-llmgw upstream --https 0.0.0.0:443 --http 0.0.0.0:80 --cert-dir ./llmgw-ca --name <上游的公网地址或域名>
```

- 第一次运行在 `--cert-dir` 里生成测试 CA（`ca.pem`、`ca-key.pem`），之后沿用，重启上游不用重新分发 `ca.pem`。证书里的名字用 `--name` 指定，可以写多次，域名和 IP 都可以；负载端连的地址（或者它的 `--sni`）必须在里面。
- 端点：`POST /v1/chat/completions`（SSE）、`GET /v1/realtime`（WebSocket）、`GET /health`（回 `ok`）。每个连接只服务一个请求：经代理入口时一个请求就是节点之间的一条新流，这正是要测的。
- 每 10 秒在标准错误上打一行计数（连接、进行中的流、事件速率、中途重置、停住、坏请求）。

## 负载端

```sh
i3t-llmgw load --scenario 场景.toml --target https://<上游>:443 --ca ./llmgw-ca/ca.pem \
    --proxy socks5://<出口节点>@127.0.0.1:1080 \
    --watch entry=state:/var/lib/i3t --out 结果.json
```

| 参数 | 含义 |
|---|---|
| `--proxy` | `socks5://出口@主机:端口`、`http://出口[:密码]@主机:端口`（CONNECT），或者 `direct`（不经代理，对照用）。用户名就是出口节点的名字或虚拟 IP，可以带等级后缀，比如 `home+c-i` |
| `--target` | `https://主机[:端口]` 或 `http://主机[:端口]` |
| `--ca`、`--sni` | 上游的 CA 证书；TLS 用的服务器名，默认是 `--target` 里的主机 |
| `--watch` | 采样一个进程的 CPU 时间和常驻内存：`名字=pid` 或 `名字=state:节点的状态目录`（命令行里带着这个目录的进程，中途重启也跟得上）。可以写多次。只在 Linux 上有效 |
| `--out`、`--label` | 结果的 JSON 写到哪里；写进报告的一句说明 |

有流没有按期望结束时退出码是 1，参数或场景文件有错时是 2。

### 场景文件

```toml
name = "示例"
duration_s = 120        # 整个运行的上限；到时还没结束的流算超时
stall_ms = 250          # 两个事件的到达间隔比上游的节拍多出这么多，算一次卡顿

[[group]]
name = "fast"
kind = "sse"            # sse 或 ws
count = 300
arrival = { ramp_s = 5 }   # "all"：同时；{ rate = 50 }：每秒 50 条；{ ramp_s = 5 }：到达速率在 5 秒里从 0 线性涨上去
start_s = 0             # 这一组从运行开始之后多久开始
prompt_bytes = [20000, 1000000]   # 提示词大小：一个数，或者 [最小, 最大]
think_ms = 1000         # 上游收到请求之后思考多久
keepalive_ms = 0        # SSE 思考期间保活注释的间隔，0 是完全静默
tokens = 500            # 事件个数（WebSocket 是每轮）
rate = 100              # 每秒事件数，0 是连接收多快就发多快
event_bytes = 40        # 每个事件里填充内容的字节数（SSE 的一个事件另外还有约 100 字节的序号、时间、哈希）
pauses = [{ after = 200, ms = 3000 }]   # 发完第 200 个事件之后停 3 秒
end = "done"            # done：正常结束；abort：发完 end_after 个事件后上游重置连接；stall：之后什么都不发，连接一直开着
end_after = 0
hold_s = 40             # stall：停住之后负载端再拿着它多久才关
# expect = "reset"      # 覆盖按 end 推出的期望结果，比如出口重启时正在跑的流应该是 reset
```

WebSocket 组（`kind = "ws"`）另有：

| 字段 | 含义 |
|---|---|
| `turns` | 几轮问答。每一轮由客户端发一条带提示词的消息开始，上游思考、发 `tokens` 个事件 |
| `binary` | 上游的事件用二进制帧（像语音输出），否则用文本消息 |
| `client_msgs` | 每一轮回答进行中客户端插进几条消息，均匀落在事件之间 |
| `client_binary_ms`、`client_binary_bytes` | 从一轮开始到这一轮结束，客户端每隔多久发一个多大的二进制帧（像语音输入） |
| `idle_ms` | 两轮之间客户端空闲多久 |
| `client_ping_ms`、`server_ping_ms` | 两边各自多久 ping 一次，0 是不 ping |

每一轮结束后客户端请上游报出它收到并验过的客户端消息和二进制帧的个数和累积哈希，必须和发出的完全一样。`end_after` 在 WebSocket 里按整个会话累计。

## 在真实的机器上跑

1. 上游放在一台有公网地址的主机上。出口节点只连公网目标：私网、回环、文档用的地址段都会被拒绝；默认只放行 80 和 443 端口，所以上游就监听这两个端口。
2. 把上游 `--cert-dir` 里的 `ca.pem` 拷到入口那台机器上。
3. 出口节点要启用为出口，入口节点要能访问它（访问规则）；网关的部署里入口和出口这一对最好设成连接常驻。
4. 在入口那台机器上：

```sh
ulimit -n 65536     # 几千条流需要几千个文件描述符；工具会自己把软上限提到硬上限，硬上限不够时先调它
i3t-llmgw load --scenario 场景.toml --target https://<上游>:443 --ca ca.pem \
    --proxy socks5://<出口节点>@127.0.0.1:1080 --watch entry=state:<入口的状态目录> --out 结果.json
```

出口那台机器上的花费要在出口上另外看（`--watch` 只能看本机的进程），比如对照运行前后 `i3t status` 或者指标接口。

先用 `--proxy direct`（入口机器直接连上游）跑一遍同一个场景，作为没有经过 ice3tier 的对照。

## 怎么读输出

每组一段：按期望结束的条数，各种结果的条数，然后各项测量的 p50 / p90 / p99 / p99.9 / 最大值（毫秒）：

| 项 | 含义 |
|---|---|
| 连接+代理握手 | 连到代理并完成 SOCKS5 / CONNECT 握手。入口一般先回成功再去连，所以这一项很小 |
| TLS 握手 | 经隧道和上游握手：第一次真正经过入口、出口到达上游的往返 |
| 首字节 | 从开始连接到收到响应的第一个字节 |
| 上传请求体 | 从开始写请求到上游读完请求体 |
| 首个事件 | 从请求发完（WebSocket：一轮的请求发出）到收到第一个事件，包含上游的思考时间 |
| 首事件迟到 | 第一个事件从上游写出到负载端收到。长时间静默之后它大，说明路断过、在重新建立 |
| 事件间隔 | 相邻两个事件到达的间隔 |
| 间隔超出节拍 | 到达间隔比上游写出这两个事件的间隔多出来的部分，也就是路上多等的。卡顿次数按它数 |
| 单向延迟 | 每个事件从上游写出到负载端收到 |
| ping 往返 | WebSocket 客户端 ping 的往返 |

"上传请求体""首事件迟到""单向延迟"是单向的量，要求两台机器的时钟一致：同一台机器（端到端测试的网络命名空间）上是准的，跨机器时差多少就错多少，只看间隔类的量（间隔超出节拍、首字节、首个事件）。

结果的分类：

| 结果 | 含义 |
|---|---|
| `complete` | 收到了全部事件和终止事件，结尾完整 |
| `reset` | 连接被重置（RST）。上游中途出错、出口掉线时应该是这样 |
| `truncated` | 没有终止事件就收到了正常的关闭（FIN；TLS 时是没有 close_notify 的 FIN，WebSocket 时是没有关闭握手）。回答被截断了，在 TCP 层却像正常结束，这是节点的错误 |
| `stalled` | 上游按要求停住之后，负载端拿着它到了时候一直没有出错 |
| `timeout` | 到了整个运行的时限还没结束 |
| `corrupt` | 乱序、丢了事件、内容被改、提示词没有完整到达 |
| `proxy_refused`、`connect_failed`、`tls_failed`、`http_error`、`error` | 代理拒绝、连不上、TLS 握手失败、上游回了别的状态码、其他读写错误 |

每条不符合期望的流（每组最多 40 条）在 JSON 里有说明、收到的事件数、开始和结束的时刻，结束时刻同时给出墙上时钟（`ended_unix_ms`），用来对照节点日志里那一刻发生了什么。

最后几行：

- 停顿：所有流的卡顿按时间合并，重叠的算一次停顿，报一次停顿牵连了几条流、持续多久。所有流共用一条 TCP 时，一个丢包会让在线的流一起停，这里就会看到牵连很多条流的停顿；
- 进程：`--watch` 的进程这段时间用了多少 CPU 秒、平均占几个核、常驻内存峰值；
- 负载端自己的 CPU 和内存，以及开始、结束时机器的平均负载。机器很忙时延迟类的数只能作参考。

## 工具自己的容量

在开发机上（14 核，同时有别的构建在跑，平均负载 7～15），负载端和上游都在本机、走 HTTPS、不经代理：

- 4000 条并发的 SSE 流，每条每秒 25 个事件：事件峰值每秒 10 万个，4000 条全部完整，间隔超出节拍的 p99.9 是 2.2 ms、最大 9.6 ms；负载端用了 37 CPU 秒（52 秒里平均 0.7 个核），常驻内存峰值 295 MB（几千份提示词和读缓冲）；
- 400 条流，每条每秒 400 个事件：事件峰值每秒 16 万个，全部完整，间隔超出节拍的 p99 是 10 ms、最大 108 ms（这时机器的平均负载升到 15），负载端用了 0.6 个核。

负载端本身不是瓶颈。经节点测量时，先用 `--proxy direct` 跑一遍同样的场景，就知道哪些数是工具和机器带来的。

## 端到端测试

`tests/e2e/test_llm.py` 在网络命名空间搭出的实验环境里用真实的节点跑这些负载：长时间静默、快速输出、WebSocket 会话、成批到达、两千条同时在线、上游出错、长距离丢包的路、出口只能走 TCP、流进行中换路、出口重启。每个场景先做检查，再打一张测量表；需要对照的场景先不经节点直连跑一遍同样的负载。整个文件跑完约 9 分钟。

```sh
cargo build --release -p i3t -p i3t-llmgw
I3T_BIN_DIR=$PWD/target/release python3 tests/e2e/test_llm.py [--long] [--keep] [--pair '{"字段": 值}'] [场景名...]
```

- `--long`：长时间静默的场景静默 10 分钟（默认 75 秒）。
- `--keep`：留下每个场景的工作目录：节点日志、场景文件、每次负载的 JSON 结果和表。
- `--pair`：给入口—出口这一对节点加上按节点对的设置（合进两边静态 netmap 里互相看到的对端条目），用来在同样的负载下对比不同的设置。所有场景的入口—出口对都经过 `apply_pair_setting` 这一个函数。
