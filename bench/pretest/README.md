# 实现前测试工具

在写产品代码之前，用来回答几个问题的最小工具：

- 节点之间一条端到端的 QUIC 连接，在各种延迟、丢包、带宽下表现如何，和 KCP、TCP 比怎么样；
- 这条连接经一个或两个只转发包的 relay 时，代价是多少，relay 自己耗多少 CPU；
- 连接中途换路（经 relay ⇄ 直连）时，上面的流断不断、停多久；
- UDP 用不了、只能把包装进一条 TCP 送到 relay 时，丢包会造成多长的停顿；
- 一条连接上跑几千条"上传请求体、等一会儿、再按节拍收小消息"的流时表现如何。

这里的代码只为测量服务，不是产品代码的雏形：没有认证，证书不校验，协议格式随时会改。

## 构建

```
cargo build --release -p i3t-pretest
cargo test -p i3t-pretest
```

## 一个二进制，四个角色

```
i3t-pretest relay --udp 0.0.0.0:20330 [--tcp 0.0.0.0:20330] [--route 节点编号=下一个 relay 的地址]
i3t-pretest serve <quic|tcp|kcp> --listen 0.0.0.0:20330 [路径参数] [传输参数]
i3t-pretest run   <quic|tcp|kcp> --connect <服务端地址> [路径参数] [传输参数] [负载参数]
i3t-pretest hop   --listen 0.0.0.0:20330 --upstream <下一跳地址>
```

- `relay`：按包头里的目的节点查表，原样转发。不解密，不缓冲，发不出去就丢。节点可以用 UDP 挂上来，也可以用一条 TCP 挂上来。
- `serve` / `run`：服务端和客户端。客户端跑完一种负载后在标准输出打一行 JSON。
- `hop`：在两条 TCP 之间搬数据的中间跳，用作"每一段各自重传"的对照组。

### 路径参数（只对 QUIC 有意义）

QUIC 连接始终把对端看成同一个固定地址，每个包实际走哪条路由下面一层决定，所以换路时连接不知道。

| 参数 | 含义 |
|---|---|
| `--id` / `--peer` | 本节点和对端节点的编号，默认客户端 1、服务端 2 |
| `--connect`（客户端）/ `--direct`（服务端） | 对端直连用的地址 |
| `--relay` | relay 的 UDP 地址 |
| `--relay-tcp` | relay 的 TCP 地址；给了就会连上去 |
| `--route direct\|relay\|relay-tcp` | 一开始走哪条路 |
| `--switch 6:direct,12:relay` | 第 6 秒改走直连，第 12 秒改回 relay。两端各自按自己的时间表切换 |
| `--tcp-queue` | TCP 中转的发送队列最多排多少个包，排满就丢 |

### 传输参数

| 参数 | 含义 |
|---|---|
| `--cc cubic\|bbr\|newreno` | QUIC 的拥塞控制 |
| `--window-mb` | QUIC 每条流的接收窗口，默认 2 |
| `--max-streams` | QUIC 允许对端同时开多少条流，默认 16384。库会为每条允许的流预先占约 100 字节 |
| `--idle-secs` | QUIC 的空闲超时，0 表示不设 |
| `--no-gso` | 不用内核的 UDP 分段卸载 |
| `--cipher aes128\|aes256\|chacha20` | QUIC 的加密套件 |
| `--kcp-mode fast\|normal`、`--kcp-window` | KCP 的档位和窗口 |

### 负载

| `--workload` | 做什么 | 主要输出 |
|---|---|---|
| `bulk` | `--streams` 条流同时上传或下载 `--secs` 秒 | 跳过预热后的平均吞吐、最长的无数据时间 |
| `echo` | 每 `--interval-ms` 发一条小消息，对端原样送回 | 往返时间的分布 |
| `mixed` | `bulk` 和 `echo` 同时跑；`--split` 让小消息另走一条 QUIC 连接 | 两者都有 |
| `llm` | `--concurrency` 个并发，一共 `--requests` 个请求：上传请求体，等 `--ttft-ms`，再收 `--tokens` 条小消息；每 `--silent-every` 个请求里有一个中途静默 `--silent-ms` | 成功与失败数、首条消息的额外等待、每条消息的延迟 |
| `setup` | 反复新建连接并收发一条消息 | 第一次访问的耗时；QUIC 另有"已有连接上开新流"的耗时 |

每个进程退出时还会报告自己用掉的 CPU 时间和内存峰值。

## 本机实验环境

`lab/lab.py` 在本机用网络命名空间、veth 和 netem 搭出下面的拓扑，然后按测试组逐个用例跑：

```
a ───────────────── b        直连
a ── r1 ─────────── b        经一个 relay
a ── r1 ── r2 ───── b        经两个 relay
```

不需要 root，脚本会用 `unshare -Urnm` 进入一个新的用户命名空间。需要系统里有 `ip`、`tc`、`ethtool`、`taskset`，内核有 `sch_netem`。

```
bench/pretest/lab/lab.py list                     列出测试组和用例数
bench/pretest/lab/lab.py run t1 t2 --secs 10      跑指定的测试组
bench/pretest/lab/lab.py run t4 --only access1    只跑名字里带这个子串的用例
bench/pretest/lab/lab.py shell                    建好拓扑后进一个 shell 手工试
```

结果按测试组写成 JSONL，每行一个用例：网络条件、客户端的输出、服务端和 relay 的输出、各网卡实际发出的字节数。同一个用例已经有结果时默认跳过，`--redo` 重跑。

| 测试组 | 内容 |
|---|---|
| `t1` | 不加任何限制：各传输的上限、每 GB 的 CPU、加密套件的差别、relay 的 CPU |
| `t2`、`t2s` | 直连，往返延迟 0 / 50 / 150ms × 丢包 0 / 0.5 / 1 / 3% × 带宽 20 / 100 / 1000 Mbit/s；多条并发流；上行 |
| `lat` | 小消息的往返延迟分布；第一次访问的建立耗时 |
| `t4` | 经一个 relay，以及同样条件下"每一段各自终结的 TCP"对照 |
| `t5` | 经两个 relay |
| `t6` | 一条连接上大流量和小消息同时跑，对比把小消息分到另一条连接 |
| `t7` | 换路：经 relay → 直连 → 经 relay |
| `t9` | TCP 中转的三种组合，发送队列长度的影响，以及给内核里未发出的数据设上限之后的对比 |
| `t10` | LLM 形状的负载 |

### 读结果时要知道的几点

- **丢包测试关掉了分段与合并卸载。** 开着的时候，netem 的一次"丢包"丢的是一整批几十个包。所以带 netem 的用例里每个包一次系统调用，CPU 数字比真实网卡上偏高；`t1` 不加 netem，卸载是开着的。
- **带宽限制处留了约 100ms 的队列。** 基于丢包的拥塞控制会把它填满，所以大流量时测到的往返时间比设定的链路延迟高。
- **本机的 TCP 只有 cubic 和 reno。** `tcp_bbr` 模块没有加载，加载它需要 root。
- **各进程固定在同一种 CPU 核上**（`lab.py` 里的 `CORES`），避免结果随调度漂移。换机器跑时要改。
- **QUIC 每条流的接收窗口默认 2MB**，单条流的吞吐因此不会超过"窗口 ÷ 往返时间"。放大窗口可以提高上限，但一条流里的空洞数超过 QUIC 库的硬上限（1024 个）时，整条连接会被关掉。重度丢包会触发，瓶颈处队列溢出造成的成片丢包也会触发。
- **QUIC 端点的内存跟"允许同时开多少条流"成正比**：100 条约 11MB，16384 条约 13MB，100 万条约 115MB。
- **TCP 中转里"内核未发出数据的上限"是用命名空间级的内核参数设的**（`net.ipv4.tcp_notsent_lowat`），只在那几个用例运行期间生效。产品里对应的是每条 TCP 上的 `TCP_NOTSENT_LOWAT`。
- **TCP 服务端的监听队列调到了 16384**（系统会再压到 `net.core.somaxconn`）。默认的 1024 会被几千个同时到达的连接挤满，那时测到的是监听队列而不是 TCP。

## 在真实链路上跑

本机环境测不了的东西要在真实机器上跑：真实的 NAT、运营商对 UDP 的限速、跨境链路在不同时段的质量。

把二进制拷到各台机器上，在有公网端口的机器上起 `serve`（和 `relay`），在另一端起 `run`。例如：

```
# 有公网地址的机器 S
i3t-pretest serve quic --listen 0.0.0.0:20330 --id 2 --peer 1

# 另一端
i3t-pretest run quic --connect <S 的公网地址>:20330 --workload bulk --secs 20 --dir down --cc bbr
i3t-pretest run quic --connect <S 的公网地址>:20330 --workload echo --secs 60
```

同一条路径上再用 `tcp` 跑一遍，两者差别很大时通常说明这条路上 UDP 被限速了。

经 relay 的情形：在第三台机器 R 上起 `relay`，两端都加 `--relay <R 的地址>:20330 --route relay`。

真实链路上两端时钟不同步，`llm` 负载里"每条消息的延迟"一项没有意义，其余各项不受影响。

### 打洞

打洞的成功率只能在真实的 NAT 后面测。需要一台有公网端口的机器当汇合点，它只告诉两个节点各自和对方的公网地址，不转发数据。

```
# 有公网地址的机器 S：开两个 UDP 端口
i3t-pretest punch rendezvous --listen 0.0.0.0:20340 --alt 0.0.0.0:20341

# 两台 NAT 后面的机器，各跑一个，会话名相同；先后启动相差不超过一分钟
i3t-pretest punch peer --rendezvous <S>:20340 --alt <S>:20341 --session home-to-phone --tries 20
```

每次尝试用一个新的本地端口：向汇合点登记，拿到对端的公网地址，双方用各自同一个端口互相发探测包，10 秒内双向都通算成功，然后在打通的洞上发 50 个 ping。输出里每次尝试一条记录：

| 字段 | 含义 |
|---|---|
| `mapped` | 汇合点看到的本节点地址 |
| `mapping_varies` | 汇合点的两个端口看到的地址不一样。为 `true` 时这台机器所在的网络基本打不了洞 |
| `peer_announced` / `peer_actual` | 汇合点通告的对端地址，和实际收到探测包的来源地址 |
| `success`、`punch_ms` | 是否打通，从拿到对端地址到双向都通用了多久 |
| `rtt_ms`、`ping_loss_pct` | 打通之后的往返时间和丢包率 |

把两端的输出都保存下来。要覆盖的组合至少有：家宽对家宽（同一运营商、跨运营商）、家宽对手机热点。
